# 架构思考框架（三关检查）

> **【通用方法论 · 项目资产】** 本文件随工具分发的版本是跨项目通用的专家标准。安装到项目后，整个 `.opencode/` 即成为你的**项目资产**——可直接改写本文件沉淀团队/项目专属规则，也可在项目 `opencode.json` 的 `instructions` 中增删规则条目。工具不预设任何项目特定内容。

> **适用时机：** 每次 code-developer 接到编码任务后、开始写代码之前
> **目的：** 防止 AI 在缺乏架构上下文的情况下直接动手导致的系统性漂移

---

## 第一关：查已有（30 秒）

在写任何代码之前，先查项目中是否有**同类功能、同类数据、同类配置**的已有实现：

```
□ 这个功能在项目中是否存在类似实现？
  → 搜索类似关键词、文件名、函数名
  → 优先扩展已有函数，不创建新文件

□ 这个数据在已有服务/模块中是否已经被提供？
  → 搜索项目中的聚合函数、Facade、Service 入口
  → 是否存在对应的已有函数或方法
  → 存在则走已有入口，不要重复造轮子

□ 这个配置项在项目配置系统中是否有定义？
  → 搜索配置文件（config.py / .env / config.yaml / application.yml）
  → 已有配置项 → 复用
  → 新增配置项必须注册到配置系统
```

**通用原则：**
```
数据读取 → 走已有聚合/读取入口
配置变更 → 走配置系统注册
HTTP 调用 → 走已有 HTTP 客户端聚合
缓存操作 → 复用已有缓存策略
```

---

## 第二关：定位置（30 秒）

确定新代码应该放在哪：

```
□ 这是新模块还是现有模块的功能扩展？
  → 现有模块 → 在现有文件上增量改（手术式修改）
  → 新模块   → 必须先检查 doc/arch/ 是否有架构建档

□ 应该在哪个层级加代码？
  → 业务逻辑 → 遵循现有分层（service/repository/controller）
  → API 层 → 遵循现有路由结构
  → 配置 → 注册到配置系统
  → 测试 → 遵循现有测试目录结构

□ 是加新函数还是改已有函数？
  → 能改已有就不要新建
  → 能扩展参数就不要加新函数

□ 是否需要在文档中注册？
  → 是 → 在产出物中标注 >>DOC_SYNC:
```

---

## 第三关：验影响（30 秒）

写之前想清楚改动会波及什么：

```
□ 改动会影响哪些消费者？
  → 改了函数签名 → 搜索所有调用者
  → 改了返回字段 → 确认所有下游不会被破坏
  → 改了 HTTP 调用 → 确认不会重复请求同一数据

□ 会引入新的外部依赖吗？
  → 新增 HTTP 客户端 → 确认是否有已有聚合入口可用
  → 新增第三方库 → 确认是否已在依赖文件（requirements.txt/package.json等）中声明

□ 缓存策略是否正确？
  → TTL 设置是否合理
  → 是否需要考虑缓存失效/降级

□ 配置项是否已在配置系统中注册？
  → 新增常量是否应该做成可配置项
  → 新增配置项是否在文档中说明
```

## 违规自检清单

交给 code-reviewer 之前，先逐条确认：

```
[  ] 没有绕过已有聚合入口直接调用外部服务
[  ] 没有直接 new 外部客户端（使用已有 HTTP 客户端聚合）
[  ] 没有硬编码配置值（使用配置系统读取）
[  ] 新增数据入口已注册到配置系统
[  ] 没有创建多余的模块级缓存（如果有已评估可复用性）
[  ] 如果改 API 签名，已标注 >>DOC_SYNC:
```

## 常见漂移模式（反面教材）

| 模式 | 描述 | 正确做法 |
|------|------|---------|
| 「顺手加个 HTTP 请求」 | 模块内直接发起外部调用 | 走已有的 HTTP 客户端聚合 |
| 「就地 new 客户端」 | 每次使用都 new 一个客户端 | 复用已有客户端实例/聚合入口 |
| 「配置硬编码」 | 超时/重试/URL 写在代码里 | 在配置系统中注册后读取 |
| 「重复造缓存」 | 新建本地 cache dict | 复用项目已有缓存策略 |
| 「擅自加新端点」 | 新增 API 路由绑定新功能 | 先确认是否匹配上层模块边界 |
