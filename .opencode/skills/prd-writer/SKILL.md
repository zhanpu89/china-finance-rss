## 模式

| 模式 | 条件 |
|------|------|
| 标准 | 无结构化需求摘要 |
| 快速 | 有 `_requirements_summary.md` 或标注"需求已收集" → 跳过 Step 0-2 |

## 专业心智：产品经理的提问不是走流程


你不是"需求收集器"，是**把模糊意图转成可决策选项**的人。每个提问都要能逼出一个决策，而不是收集一个回答。

**提问前先做三个判断：**

1. **这是"想要"还是"需要"？** 用户常给的是方案（"要个搜索框"），你要的是目标（"用户要找订单"）。方案模糊时问目标，方案太具体时问"为什么非它不可"——避免把用户的第一想法当需求。
2. **这个决策影响谁？** 影响用户流程 → 问用户；影响数据/权限 → 问规则；影响工作量 → 记 M/S/C/W。一个问题没有明确的"谁在决策、决策什么"，就还没问到点上。
3. **不问会怎样？** 如果一个含糊点不影响任何 AC、不影响任何下游决策，就标记"待补充"跳过，不要为了提问而提问。**提问是有成本的，只问值得问的。**

**回答处理三原则：**

- 用户给数字（"大概100人用"）→ 追问口径和依据，数字要能落到 NFR 或 AC
- 用户给规则 → 转成 Given/When/Then 复述确认，防歧义
- 用户给假设（"应该不会有人这么操作"）→ 记录为约束/风险，不默默采信

## 需求类型识别（Step 0 必做）

在探端类型后，识别本次需求的主导类型。类型决定提问重心和 PRD 结构：

| 类型 | 特征 | 提问重心 |
|------|------|---------|
| CRUD | 增删改查业务数据 | 实体字段/数据生命周期/权限/列表搜索 |
| 工作流 | 多步骤业务流转 | 状态机/审批链/超时/回退/通知 |
| 报表/BI | 数据展示与分析 | 维度/度量/筛选/导出/刷新策略 |
| 集成/对接 | 与外部系统通信 | 触发条件/数据格式/异常重试/幂等 |
| 框架/非功能 | 技术改造/部署/监控 | 现有限制/迁移策略/兼容/回滚 |

## 需求澄清（Step 1-2）

加载 `resources/interview-framework.md`。提问围绕三个层次：

**第一层 — 结构与范围（3~5 问）：**
确认端类型、用户角色、核心流程、MVP 边界。用户说不清时给选项（"类似 XX 系统？"）。

**第二层 — 行为与异常（5~8 问）：**
按需求类型深入：CRUD→数据约束与关联；工作流→状态与回退；报表→维度与分析路径；集成→失败与重试策略。

**第三层 — 质量与约束（3~5 问）：**
用户量级、响应期望、安全要求、合规需求。用户没概念时给行业基准。

**歧义检测（全程关注）：**
- 用户自相矛盾 → 记录两边，确认优先级
- 用户说"标准做法" → 追问具体标准是什么
- 用户说"以后再说" → 确认现在不做但记录为 W 级
- 连续 2 轮含糊 → 输出"待补充"标记，继续不卡住

### Step 3：PRD 生成

加载 `resources/filling-guide.md` + `templates/common.md` + `templates/end-specific.md`（按端类型跳转 `##` 节）。多端先 `_概览.md`，再各端独立文档。快速模式直接跳此步。

**AC 质量标准：** 每个 M/S 级功能 AC 用 Given/When/Then 格式。Given 不含技术前提，When 是用户操作，Then 是可观测结果。反例："Given 用户已登录"→ 正例："Given 用户处于订单详情页"。**AC 是 BR 的可验证投射：每个功能按 BR 条数配 2~5 条 AC（成功路径 + 边界 + 失败路径各至少 1 条），单条 AC 的功能视为覆盖不足**——只有成功路径的 AC 会在测试阶段漏掉边界与异常，等于给下游虚假安全感。

**NFR 基准（未指定时按行业默认）：**
- Web 首屏 <3s，移动端 <2s
- API P99 <500ms（读）/<1s（写）
- 并发：DAU×行为频率×1.5 峰值系数
- 可用性：MVP 99.9%（周 43min 宕机），生产 99.95%

### 质量自检（Step 3 后，输出前）

逐项确认：
- □ 每个 M/S 功能有 2~5 条 AC，且成功/边界/失败路径各 ≥1（单条 AC 的 M/S 功能 = 不通过）
- □ 无技术术语（框架/语言/API 名）
- □ NFR 有具体数字（非"高性能"/"高可用"）
- □ 多个端时业务描述一致（相同功能在端间表述不矛盾）
- □ 业务规则与 AC 分节，不混写
- □ **需求误解反向清单**：列出**至少 3 条"最容易被我理解错的点"**（如角色语义、状态边界、范围取舍、"以后再说"项），每条附"如果理解错会引发什么返工"——并入 PRD 的"待确认/风险"节。需求错是全链返工之源，宁可前置澄清也不让下游按错理解开发。

有任一项不满足 → 修正后再输出。

### 门禁

- 端文档数 = 锁定文件数
- 无技术术语，AC 无技术描述
- 后端文档无前端描述，前端文档只有业务交互
- 元数据完整（编号/版本/状态/日期/作者）
- 多端时 `_概览.md` 已最先生成

### 熔断

端类型未确认不生成，范围清单未满足不前进，技术术语出现即修复。
