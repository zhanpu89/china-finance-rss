# 代码评审反模式库（Review Checklist）

> 这不是"检查项"清单，是被验证过"**一定会出错**"的反模式集合。评审时不是逐条对照，而是带着这些模式去读代码——命中越多，越要警惕。下面的每个反模式都给出**证据链模板**：当 {输入} 发生时，会 {后果}，因为 {代码路径}。
>
> **与 SKILL.md 的 Dim 对应：** 六个类别一一映射审查维度——Dim 1→[数据与正确性]、Dim 2→[并发]、Dim 3→[资源与性能]、Dim 4→[安全]、Dim 5→[结构与可维护性]、Dim 0→[契约一致性]、Dim 6→[前端]。评审报告 D{dim} 详情里注明命中的反模式名。

## Dim 1 — 数据与正确性反模式

| 反模式 | 识别特征 | 后果（证据链锚点） | 等级 |
|--------|---------|-------------------|------|
| **魔法数字/字符串** | 硬编码 `100`、`"ACTIVE"`、超时 3000 散落 | 行为无法追溯、一处改漏 | P2 |
| **隐式状态转换** | 用清 0、置 null、改 flag 代替状态机 | 非法状态可达成，未知状态无处理 | P1 |
| **重复定义数据源** | 同一字段在 DTO/vo/entity 各写一份 | 改一处不同步 → 数据不一致 | P1 |
| **返回裸引用/可变对象** | getter 返回内部 List/Map 未拷贝 | 调用方能改内部状态 → 隐蔽 bug | P1 |
| **宽泛异常捕获** | `catch (Exception e) {}` 吞异常/空捕获 | 错误被静默，难定位，掩盖真实失败 | P0/P1 |
| **不检查空值/可选** | 对可能为 null 的对象直接 `.field` | NPE / 空指针崩溃 | P0 |

## Dim 2 — 并发反模式

| 反模式 | 识别特征 | 后果 | 等级 |
|--------|---------|------|------|
| **未同步的共享可变状态** | 静态/全局变量并发读写无同步 | 数据竞争 → 脏读/覆盖 | P0 |
| **双重检查锁陷阱** | 单例 `if null { lock; if null init }` 无 volatile | 指令重排 → 拿到半初始化实例 | P1 |
| **集合并发修改** | 遍历时增删 HashMap/List | ConcurrentModificationException | P1 |
| **线程池资源耗尽** | 无限提交任务/线程阻塞无超时 | 线程饥饿 → 卡死 | P1 |
| **非原子读改写** | `count++`、先查后改无锁/无版本 | 竞态 → 计数/状态错 | P0 |

## Dim 3 — 资源与性能反模式

| 反模式 | 识别特征 | 后果 | 等级 |
|--------|---------|------|------|
| **N+1 查询** | 循环内逐条查 DB/慢接口 | 请求数随行数爆炸 → O(n²) | P1 |
| **大事务** | 事务内做网络 IO/长循环 | 锁持有久 → 死锁/吞吐崩 | P1 |
| **资源泄漏** | 连接/流/游标未 try-with-resources | 连接耗尽 → 级联故障 | P1 |
| **内存无限增长** | 无界缓存/List 无限 append | OOM | P1 |
| **字符串拼接循环** | 循环里 `+=` 拼大字符串 | 大量临时对象 → 内存压力 | P2 |
| **缓存穿透/击穿/雪崩** | 查询直接打 DB 无空缓存/n 击穿防/过期打散 | 依赖被打垮 | P1 |

## Dim 4 — 安全反模式

| 反模式 | 识别特征 | 后果 | 等级 |
|--------|---------|------|------|
| **SQL/NoSQL/命令注入** | 字符串拼接查询/命令，未参数化 | 注入 → 数据泄漏/破坏 | P0 |
| **水平越权** | 用前端传入的 ID 直接查资源，未校验归属 | 越权访问他人数据 | P0 |
| **垂直越权** | 未校验角色直接执行管理操作 | 越权执行管理功能 | P0 |
| **敏感信息泄露** | 日志/响应泄漏密码/token/密钥/内网信息 | 凭据暴露 | P0 |
| **不安全反序列化** | 直接反序列化不可信输入 | RCE | P0 |
| **明文存储密码** | 密码用明文/弱哈希(如明文) | 撞库风险 | P0 |

## Dim 5 — 结构与可维护性反模式

| 反模式 | 识别特征 | 后果 | 等级 |
|--------|---------|------|------|
| **上帝对象** | 单类职责过多、字段/方法爆炸 | 难测试难维护、耦合 | P2 |
| **过度工程/过早抽象** | 为一次使用建接口/工厂/继承层级 | 复杂度无价值 → 难读 | P2 |
| **空对象/幽灵对象** | 需要特意判空才知道没数据 | 隐蔽逻辑错误 | P2 |
| **复制粘贴代码** | 大段相同逻辑存在于多处 | 改一处漏一处 | P2 |
| **注释说"是什么"不说"为什么"** | 注释复述代码，不提设计意图/权衡 | 迁移时无从判断 | P2 |
| **圈复杂度高** | 方法嵌套 if/switch 过多(>15) | 难测难审易漏分支 | P2 |

## Dim 0 — 契约一致性（全栈最高优先）

- **以详设 OpenAPI 为唯一来源**。后端接口路径/方法/字段与规范比对。
- 规范对则代码 bug；代码对则需 DOC_SYNC（但有契约修改权在编排层）。
- 前端 types/字段名/类型、api/URL 必须与后端一致（双重不一致 = P0）。
- **代码没有的逻辑就是没有实现**——不为"看实现没有就假设有"。

## 评审方法（跨维度，不归属特定 Dim）

1. **先读 diff** 理解变更范围，再聚焦高风险区（改动大的、涉及钱的、安全/并发边界）。
2. **逆向扫描**：恶意输入/竞态/依赖失效/隐式假设/性能悬崖/测试盲区，六问。
3. **每条发现自带证据链**：当 {输入} → {后果}，因为 {路径}。写不出后果 = 降级或删。
4. **最坏后果排序**：50 条 P2 不敌 1 条 P0。先想后果再定等级。
5. **报告开头 1-2 句总评**：让开发者知道哪 3 条最重要。

## 提交前自检

- □ 我给了每条 P0/P1 具体修复方向（哪个文件哪段）？
- □ 我确认了契约一致性（全栈模式下 OpenAPI 是来源）？
- □ P0/P1 只记录可复现问题，没把"意见"当"问题"？
- □ 报告标注了哪个反模式被命中（便于开发者定位）？
