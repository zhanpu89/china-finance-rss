# 需求评审（Check-Req）

> 评审目标：这份 PRD 让架构师和详设工程师**能不返工**地做下去。每个检查项给"怎么查"。

## 一、需求质量

| 检查项 | 怎么查（可操作锚点） | 缺陷等级 |
|--------|---------------------|---------|
| 背景/目标/用户已定义 | 读背景节能回答"解决什么问题/给谁用"；成功指标可量化（不是"提升体验"） | 无目标 = P1 |
| 主流程完整 | 核心业务端到端流程可走通（谁发起→经过哪些动作→结果是什么） | 流程断链 = P1 |
| 无技术描述 | grep 框架名/语言/API/数据库词。PRD 说技术方案 = 越权 | 技术词 = P1 |
| 内部一致性 | 同一需求在不同节/不同端描述是否矛盾；前后矛盾要标优先级 | 矛盾 = P1 |

## 二、AC 质量（M/S 级功能）

| 检查项 | 怎么查（可操作锚点） | 缺陷等级 |
|--------|---------------------|---------|
| 每 M/S 功能有 AC | 逐个 M/S 功能核对，无 AC 的功能 = P1 | 缺 AC = P1 |
| AC 数量与分布 | 每个 M/S 功能 2~5 条 AC，成功/边界/失败路径各 ≥1（单条 AC 或只有成功路径 = 伪覆盖，等同缺 AC） | 覆盖不足 = P1 |
| AC 用 Given/When/Then | Given 不含技术前提（"已登录"是技术前提）；When 是用户操作；Then 是可观测结果 | 反例 Given = P1 |
| AC 可测试 | 每条 AC 能转成测试用例（有明确输入与断言） | 无法测试 = P1 |
| 异常/边界覆盖 | 至少：输入非法/无权限/数据不存在/并发冲突/超时，这几类有 AC 或有明确"此处不处理" | 异常空白 = P1 |

## 三、逆向流程（最易漏）

**每有 Create 必有对应 Delete/停用/解绑**；每有状态推进必有逆向路径（驳回/取消/回滚/退款）。缺逆向 = P1。

## 四、需求边界

| 检查项 | 怎么查（可操作锚点） | 缺陷等级 |
|--------|---------------------|---------|
| MVP 边界明确 | "本期不做/以后再说"有标注（W 级）；未标注的含糊范围 = P1 | 范围含糊 = P1 |
| 非功能有数字 | NFR 用具体值（P99 <500ms/99.9%可用/日活×1.5），"高性能"= P1 | 模糊 NFR = P1 |
| 优先级完整 | M/S/C/W 分级清楚，无 M 级却无 AC 的情况 | 优先级缺失 = P2 |

## 五、结论判定

- **P0 存在** → ❌（安全/数据类）
- **无 P0，P1 > 2** → ⚠️ 有条件
- **无 P0，P1 ≤ 2** → ✅ 通过

**信息缺失 >30% → ❌**（标记缺失节返回）。
