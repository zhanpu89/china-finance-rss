# 技术选型决策框架（Tech-Selection）

> 这不是技术目录，是**选型决策的思维框架**。技术选型的质量在于"判断依据"是否充分，不在于清单全不全。每个选型必须产出 ADR：选 A 因为 X，不选 B 因为 Y，当 Z 发生时换 B。

## 一、选型前的四问（先于查表）

| 问题 | 判断依据 |
|------|---------|
| 这个系统最难的地方在哪？ | 数据一致性？高并发？跨服务？——技术选型要服务难点，不是堆新技术 |
| 团队技术储备是什么？ | 没人会的技术 = 巨大的隐性成本（维护、招聘、踩坑） |
| 可逆性如何？ | 低可逆（数据模型/协议）多方案深对比；高可逆（端口/版本）快速定 |
| 规模与增长预期？ | 10 万用户和 1000 万用户的选型完全不同；按真实预期选，不按"万一"选 |

## 二、数据库选型（最容易犯错的决策）

| 场景 | 推荐 | 判断理由 | 何时不选 |
|------|------|---------|---------|
| 通用 OLTP、强一致、事务 | PostgreSQL 14+ / MySQL 8 | 成熟、生态全、事务可靠 | 数据量超大或需要分布式事务 |
| 高并发读写、需要扩展 | TiDB / CockroachDB | 分布式、水平扩展、兼容 MySQL | 团队无运维经验 / 数据量小 |
| 缓存/热点/会话 | Redis 7+ | 内存级快、数据结构丰富 | 需要持久化强一致（用 DB） |
| 文档/半结构化 | MongoDB | 灵活 schema、海量文档 | 强事务、复杂关联查询 |
| 搜索 | Elasticsearch | 全文检索、聚合分析 | 数据量小用 DB 的 LIKE/全文索引 |

**数据库决策必答：** 一致性级别（强/最终）、跨表事务需求、分片/分库分表阈值（何时拆）、备份与恢复策略。

## 三、消息队列选型

| 场景 | 推荐 | 判断理由 |
|------|------|---------|
| 金融级可靠、事务消息 | RocketMQ | 事务消息、顺序消息、死信完备 |
| 标准企业集成、路由 | RabbitMQ | 灵活路由、成熟管理、易上手 |
| 海量日志/吞吐优先 | Kafka | 高吞吐、分区顺序、流处理生态 |
| 轻量解耦、快速落地 | 本地消息表/开箱即用 MQ | 避免引入重依赖 |

**MQ 决策必答：** 消息顺序需求、投递可靠性（at-least-once/at-most-once）、死信与重试、消费幂等。

## 四、后端框架

按 LC-001 定语言，框架遵循语言生态主流（Spring Boot / FastAPI / Gin / NestJS）。选型理由只需一条："团队主流 + 生态成熟 + 与项目类型匹配"。**不要为了"新"换框架。**

## 五、前端

按 LC-FE-001：Vue3 + Pinia / React + Zustand。选型一致，不混用。状态管理选与框架配套的，避免多套状态库。

## 六、SAD 层协作边界

| 产出物 | system-architect | task-decomposer |
|--------|-----------------|-----------------|
| 数据模型 | 核心表 + 关键字段（非完整 DDL） | 完整 DDL（详设第 6 节）含索引与约束理由 |
| 接口 | 端点列表（非 OpenAPI Schema） | 完整 OpenAPI 3.0（详设第 3 节） |
| 选型 | 选型论证 + ADR（低可逆深对比） | 不重新选型，按 SAD 实现 |

## 七、提交前自检

- □ 每个驱动因素收敛成一个明确结论（不是"A/B 各有优劣"）
- □ 低可逆决策有 ADR（背景/选项/决策/理由/影响）
- □ 技术选型有"不选其他"的对比理由
- □ 假设被显式化（量级/一致性/增长预期）
