# NFR 量化方法论（NFR-Quantify）

> PRD 里"高性能/高可用/支持海量"这类模糊词，架构师必须在 SAD 里量化成可验收的数字。**不能量化的 NFR = 未定义的 NFR**。给每个模糊表述套用下列模板。

## 一、模糊表述 → 量化映射

| PRD 表述 | 需要量化的维度 | 量化模板 | 默认值（未指定） |
|---------|---------------|---------|-----------------|
| "高并发" | 峰值吞吐 | 峰值 TPS = DAU × 行为频率 × 峰值系数 | 峰值系数 1.5 |
| "快速响应" | 延迟 | P99 / P50 毫秒，区分读/写/批量 | Web 首屏 <3s，移动 <2s；API 读 P99<500ms / 写 <1s |
| "高可用" | 可用性 | 可用性 % / 年停机预算 / RTO / RPO | MVP 99.9%（周 43min），生产 99.95% |
| "海量数据" | 数据量级 | 日增量/月增量/年总量 / 单表行数阈值 | 单表 >5000 万需分表策略 |
| "支持……用户" | 并发规模 | 并发连接数 = 在线用户数峰值 × 连接复用率 | — |
| "安全" | 安全等级 | 加密标准 / 认证方案 / 合规要求 | TLS1.2+，密码强哈希 |
| "实时" | 数据新鲜度 | 秒级/分钟级延迟要求 | 明确 N 秒内可见 |

## 二、量化落地公式

- **峰值 TPS** = DAU × 每用户日均操作数 × 高峰集中系数（业务峰 / 全天平均，常 2~4）
- **并发连接** = 在线峰值 × 平均并发因子（0.1~0.3）
- **容量** = 预估 × 1.5~2 缓冲
- **存储** = 单记录大小 × 日增量 × 保留期 × 系数

## 三、不可量化时的处理

- **不编造**：拿不到依据的数字标"待确认"，不塞一个假装精确的数。
- **给区间 + 依据**："预估 DAU 5k~10k，按 10k 峰值系数 1.5 = 15k TPS"——把推导过程写出，可复核。
- **关联影响**：量化的 NFR 要落到下游——影响选型（要缓存/要 MQ）、影响容量（要分表/要多副本）。

## 四、自检

- □ 每个 NFR 有具体数字，无"高性能/高可用/大规模"裸词
- □ 数字给出了推导依据（不 naked number）
- □ 量化结论影响了架构决策（不是写了数字却跟后面的设计脱节）
- □ 无法确定的量标了"待确认"，未假装精确
