## 1. 背景与目标

系统为短线交易者提供三层数据能力：RSS 快讯（5 源 7x24）、REST 行情快照（个股 / 板块 / 市场）、SSE 实时推送（按**订阅域最短 TTL** 推送全量快照帧：`quote` 域 **L0=4s**、`fundflow` / `timeline` 域 L1=8s；帧含**价格 + 五档盘口**）。当前健康基线（**现行口径 · v0.10 订正**）：**514 个单元用例全绿**（断言约 1605 处；含 RSS 条件请求 24 条 + P8 F1–F7 修复新增用例 + **P8 F8 锁表收敛用例 `SRV-T71`/`T72` + `T-CACHE-35`** + **P8 后续 `T-CACHE-36` ④⑤ / 告警去重用例 / `SRV-T73` 等**；v0.8 基线为 504、v0.9 时点基线为 511——原「51 个」为早期基线，461 / 467 / 491 / 504 / 511 为中间 / 时点基线，见 §9.1；**以 `tests/` 实测与 `doc/tester/` 报告为准**）。**口径区分（防对不上账）**：`server.md` §8 的测试要点**设计编号 75 条**（另含 `cache.md` `T-CACHE-36`、`metrics.md` `MET-T18`）是**设计编号数**，**不等于**实测 unittest 的 **514 个方法数**（二者不得混用）；集成侧另有 **P6d 25/25（`integration-report.md` v2）+ 7/7 端点（`integration-gate-report.md`）**。**RSS 响应另支持 HTTP 条件请求**：内容未变时下游可凭弱 `ETag`（`If-None-Match`）**或** `Last-Modified`（`If-Modified-Since`）换取 **`304` 零 body**（省去本次轮询的整份 feed 体；`Last-Modified` 语义见 §3.2 AC-A13——**表示最后一次变更的时刻**，故内容未变跨 TTL 重生成亦得 304），**不带条件头的客户端行为与旧版逐字一致**（§3.2 AC-A13）。

本次围绕三个指标定义可量化的需求边界与验收：

| 指标 | 体检目标 | 用户视角收益 |
|------|---------|-------------|
| 高效 | 低延迟 / 高吞吐 / 资源有界 | 盘中点开即见、轮询不排队、长连接不拖垮服务器 |
| 准确 | 不丢不错 / 分层一致 / 语义明确 | 推送帧完整有序、无 120s 级旧数据、错误可区分 |
| 稳定 | 不崩不死锁 / 优雅降级 / 超时兜底 | 上游或 Chrome 故障时系统仍可用、过载按约定拒绝 |

| P1 手动短线交易者 | 日内盯盘 | 盘中每 10-30s 轮询行情快照 + 订阅 RSS 快讯 | 时效敏感：板块异动→立即查个股 / 资金流 |
| P2 量化策略终端 | 程序化订阅 | SSE 长连接订阅 50-200 码，断线 1 tick 内重连 | 帧完整性与顺序性敏感，容忍丢旧保新 |
| P3 盘面监控人 | 板块异动监控 | 热点时段突发并发读热板块 / 龙虎榜 + 批量个股 | 瞬时流量可达均值 5-10 倍（偶发热点） |

### 2.2 核心场景（SCN 编号供 AC 溯源）

- **SCN-1 盘中快照轮询**：09:30-11:30 / 13:00-15:00 交易时段，P1 高频轮询个股详情 / 资金流 / 分时 + 板块列表；缓存命中要求毫秒级，回源秒级。
- **SCN-2 快讯跟进**：P1 订阅 5 源 RSS，L3=30s 新鲜度；热点事件时段多源同刷。
- **SCN-3 SSE 实时推送**：P2 建组订阅（POST）→ SSE 长连接按**订阅域最短节拍**（`quote` 组 L0=4s；混合组取最短，3 域组亦 4s）收全量快照帧（价格 + 五档盘口）；慢客户端不拖垮广播；僵尸组超时回收。
- **SCN-4 瞬时热点**：板块异动触发 P1/P3 同时涌向板块 + 批量个股接口，流量陡增 → 有界拒绝优先于无限排队。
- **SCN-5 上游降级**：第三方行情 API 超时 / 风控或 Chrome 重启窗口，系统降级为结构化错误或 REST 替代路径，主流程不中断。

### 2.3 场景特征约束（设计输入）

- 盘中高并发短轮询 + 长连接**并存**：主端口 8053 与流端口 8054 隔离，互不饿死。
- 行情时效敏感：交易时段 TTL 分层 **L0=4s（`quote` / `depth`，最快层）** / L1=8s / L2=12s / L3=30s / L4=300s 是「准确」的基准口径；**非交易时段全部钉在基线（120s / 120s / 120s / 180s / 300s）**，不额外打上游。
- **SSE 节拍 = 订阅域最短 TTL**（各订阅域 tier 取 `min`）：`quote` 单独订阅走 **L0=4s**，含 `fundflow` / `timeline` 的混合组同样取最短（4s）；慢域在中间拍**命中缓存、不发上游请求**（按域分拍），故 4s 节拍不会使其上游负载翻倍。无活跃订阅时空转仍保持 L1 基线。
- 偶发瞬时热点：突发并发按均值 5-10 倍估算预算。
- 上游为免费第三方接口：无 SLA，失败属常态 → 降级路径是硬需求而非可选。

## 3. 三指标需求定义与验收标准

> AC 编号：`E-高效`、`A-准确`、`S-稳定`；每条 AC 标注【模块】并给出 Given/When/Then。
> 延迟口径 = 服务端 handler 处理耗时，不含客户端网络 RTT（如理解有误见 §5 误解清单 #1）。

### 3.1 高效（Efficiency）

**EFF-1 延迟目标**

| 路径 | 指标 | 建议值 | 备注 |
|------|------|--------|------|
| 本地缓存命中 | P95 / P99 | ≤ 5ms / ≤ 15ms | 待 P6c 实测校准 |
| 上游命中（REST 回源） | P95 / P99 | ≤ 1.2s / ≤ 3s | 含 10s 超时内的正常回源；待校准 |
| CDP 命中（页面数据就绪） | P95 / P99 | ≤ 3s / ≤ 5s | 待校准 |

- **AC-E1【server.py】本地缓存命中延迟**：Given 目标端点缓存已预热（含有效数据），When 以 20 并发连续请求 1000 次，Then 服务端处理耗时 P95 ≤ 5ms、P99 ≤ 15ms，且 0 个 4xx/5xx。
- **AC-E2【cache.py】回源延迟上界**：Given 某 REST 端点缓存冷（需回源）且上游正常，When 单次请求，Then P95 ≤ 1.2s、P99 ≤ 3s，且任何单请求 ≤ 15s（超时兜底见 AC-S7）。
- **AC-E3【cdp_engine.py】CDP 路径延迟**：Given CDP 页面数据已就绪，When 连续请求 CDP 依赖端点 200 次，Then P95 ≤ 3s、P99 ≤ 5s，且 0 次断连无响应。

**EFF-2 吞吐与连接容量**

| 场景 | 容量 | 判定线 |
|------|------|--------|

- **AC-E4【server.py】混合读吞吐**：Given 以缓存命中为主的混合读负载（模拟 SCN-1 + SCN-4 混合），When 维持 ≥ 100 req/s 共 5min，Then 错误率 = 0，且**对照窗口 `[180,300]`s 的 P99 不劣化超过基线窗口 `[60,180]`s 的 20%**。★ **v0.11 校准（判据窗口修正 · 阈值 20% 不变 · B-8 闭环）**：判据由 v0.10 的「后 3min（`[120,300]`s）vs 前 2min 基线（`[0,120]`s）」改为「对照 `[180,300]`s vs 基线 `[60,180]`s」——原 **A 窗口覆盖冷启动瞬态**（终端缓存/负缓存/首批回源/连接池预热），实测 4/5 次 **A > B**（A P99 6.60–25.15ms vs B 6.32–8.66ms，波动 3.8×），判据实际度量「**瞬态多重**」而非「稳态不退化」（**瞬态越轻越易 FAIL**：上轮唯一 FAIL 即 A「异常干净」⇒ 悖论）；**基线后移剔除前 60s 瞬态**后，`doc/tester/AC-E4_尖峰因果与判据稳定性.md` 诊断口径（窗口 `[60,180]` vs `[180,300]`）实测 **5/5 ≤ 1.0**（0.2486 / 0.8814 / 0.9728 / 0.9708 / 0.4834，3 次聚集 0.88–0.97）⇒ **判据收敛**；陪裁登记：候选②（≥3 次取中位数）/③（5s 分桶 P99 中位数）更鲁棒但改动更大，留作后续。**本次为判据定义修正（校准），非放宽验收**——阈值 20% 不变、负载场景不变、只改比较窗口（排除启动瞬态段）。
- **AC-E5【stream.py】广播吞吐**：Given 100 个 SSE 连接订阅同一 200 码 × 3 字段组，When 一个 tick（该组订阅域最短 TTL）完成刷新并广播，Then 从 tick 开始到全部连接入队完成耗时 ≤ 1s，且任一连接队列丢弃 ≤ 1 帧（丢旧保新：允许丢旧帧，不允许丢最新帧），且每一连接收到的帧满足 §3.2 AC-A1 的字段契约（含元信息与 `depth` 语义）。**内容未变的拍按 AC-A2 不重复广播**（发送层去重，不构成本判定的失败）。

- **AC-E6【cache.py】URL 缓存有界**：Given 服务已连续运行且已请求超过 2500 个不同 URL，When 检查缓存条目数，Then 条目 ≤ 2000，且已被淘汰的 URL 下一次请求必然触发回源（不被旧数据命中）。
- **AC-E7【stream.py】连接与队列有界**：Given 100 个连接中有 1 个慢客户端（不读 socket），When 持续推送 300s，Then 该连接缓冲帧数 ≤ 8，单连接缓冲内存 ≤ 8 × 单帧上限，进程内存不因该连接持续增长（**临时上限占位：RSS 增量 ≤ 256MB**，即「100 连接 × 8 帧」队列缓冲总上界，属待校准项，P6c 实测后以实测分位数替换）。
- **AC-E8【server.py】线程池有界拒绝**：Given 上游被模拟为阻塞（请求不返回），When 注入 200 个并发请求，Then 线程数 ≤ 20 + 常驻后台线程数，达 inflight 上限后新请求立即收到 503，且无排队积压（队列长度不增长）。
- **AC-E9【server.py】龙虎榜缓存有界（R15）**：Given 龙虎榜端点 `/ths/longhu` 已配置 L4 TTL 缓存（日更数据，交易时段 TTL ≥ 300s），When 连续 10 次请求（间隔 5s），Then 首次请求触发上游回源、后续 9 次命中缓存（上游请求计数 = 1），且缓存命中延迟 P95 ≤ 5ms。

**EFF-5 订阅刷新节拍与端到端新鲜度（L0 新增）**

| 订阅形态 | 节拍（tick = 订阅域最短 TTL） | 端到端刷新周期目标 |
|---------|----------------------------|------------------|
| `fields=["quote"]`，50 码 | **4s（L0）** | **≤ 4s**（每拍真刷新，含五档） |
| `fields=["quote","fundflow","timeline"]`，50 码 | 4s（取最短） | **≤ 8s**（`quote` 每拍真刷新；慢域按域分拍，每 2 拍一次 = 8s） |
| `fields=["fundflow"]`（仅慢域） | 8s（L1） | ≤ 8s |
| 无活跃订阅（空池空转） | 8s（L1 基线） | —（无客户端可见帧） |

- **AC-E10【stream.py】订阅节拍与端到端刷新周期**：Given 交易时段、服务已预热（连接池与上游可用），When 分别以 `fields=["quote"]` 与 `fields=["quote","fundflow","timeline"]` 各订阅 50 码并连续观察 ≥60s，Then ① **节拍 = `min`(各订阅域 tier TTL)**（`quote` 组 4s、3 域组 4s；仅慢域组 8s；无订阅 8s 基线）；② **`quote` 50 码的端到端刷新周期 ≤ 4s**——每拍**真刷新**，不得隔拍跳过（识别特征：相邻两帧内容不得**成对相同**）；③ **3 域 50 码 ≤ 8s**（`quote` 域每拍，`fundflow`/`timeline` 域每 2 拍各刷新一次）；④ `lag=0`、`missing=0`、`stale=0`、`degraded=0`、`slip=0`。**冷启动豁免（仅一轮）**：进程**首个** refresh 轮因冷路径（空连接池 / 无 DNS 缓存 / 冷 sector 缓存）超预算时**不计数** `degraded`/`slip`，此后每一轮如实计数（空轮不消耗该豁免）——故冷启动轮的节拍/刷新周期允许一次性偏差，不得据此放宽稳态目标。
  **实测值（容器内 50 码，2026-09-17）**：`quote` 稳态节拍 **4.05s**（3.61–4.39s）、`lag=0`；冷启动首帧 **0.82–4.26s**（另一次「进程冷首脑」样本 9.87s，已由「空闲首订阅唤醒」修复，残差 2–7ms）；3 域首帧 **3.46–3.54s**（σ≈0.04s）、首全量帧 2.17–4.19s、`lag=0`。**待盘内终验**：`refresh_epoch`（每拍真刷新）的直接验证在**盘后 tick=120s** 的等价条件（TTL==tick）下完成（连续两拍严格 120.0s 且内容更新，无隔拍跳过），**盘中 4s 档的端到端刷新周期仍待交易时段复测**——这是本 AC 唯一的「建议值 / 待校准」项。
  **编号理由**：原 AC 体系无「SSE 刷新节拍 / 端到端新鲜度」条目（原口径散落在 AC-A3 的 TTL 分层与 AC-S11 的 tick 描述中），L0 档与 `refresh_epoch` 是**新增对外可观察承诺**（客户端可见节拍与刷新周期），故在「高效」序列**追加** AC-E10，不重排既有编号。

**EFF-6 RSS 响应带宽（条件请求收益，v0.7 新增）**

| 情形 | 响应体 |
|------|--------|
| 内容未变 + 下游带 `If-None-Match`（`ETag` 通道） | **0 B**（`304`：无 body、无 `Content-Encoding`、无 `Content-Length`） |
| 内容未变 + 下游**仅**带 `If-Modified-Since`（IMS 通道，v0.8 / F1） | **0 B**（`304`：同上）——`Last-Modified` 表示最后一次变更时刻，**跨 TTL 重生成不前进** ⇒ IMS-only 客户端同样得 304 |
| 内容变化 / 无任何条件头 | 完整 feed 体（单源实测 `Content-Length` `12901 B`（`/jin10/flash`）– `45003 B`（`/cls/telegraph`）） |

- **量化收益**：内容未变时下游单次轮询省去整份 feed 体（**~37–45KB/次** 量级 → **0 B**）；**省的是客户端带宽，不是上游请求**——上游回源仍由缓存 TTL 决定（职责边界见 §3.2 AC-A13）。
- **通道修正（v0.8 / F1）**：v0.7 曾登记「IMS-only 通道收益≈0」（旧 `Last-Modified` 取缓存写入时刻 ⇒ 跨 TTL 边界必 200）。**该取舍已修复**：`Last-Modified` 改为**表示最后一次变更的时刻**，IMS-only 客户端在**内容未变**时跨 TTL 重生成**同样得 304**——`ETag` 与 `Last-Modified` 两个通道**收益对等**（原按推荐节奏 `<ttl>1</ttl>`=60s ≥ 盘中 TTL 30s 命中的正是 TTL 之后）。
- **可观测性（v0.8 / F3）**：304 计数 `http_304_total` 单点计数（`/healthz` 可见），**「省带宽」据此可被生产验证**；计数**停滞即「派生元数据抖动 ⇒ 永远 200」回归的报警信号**（详见 AC-S10）。
- **校验器成本**：服务端每次 RSS 请求一次规范化投影 + sha256 + 3 次正则 ≈ **0.1–0.2ms**（远小于同响应 gzip 与网络收益）。

### 3.2 准确（Accuracy）

**ACC-1 推送帧完整与有序（SCN-3）**

- **AC-A1【stream.py】帧完整性（含五档与元信息）**：Given 组订阅 50 码 × 3 字段且持续推送，When 客户端接收连续 200 帧，Then 每帧满足：① `items` **覆盖全部订阅码**（每码一项，该码无数据的字段为 `null`，**不得省略码**）；② 每码含全部 3 个订阅字段；③ 元信息字段齐备——`codes_total`（= 订阅码数）、`fields`（= 订阅字段集）、`missing` / `missing_count`（无数据码，排序）、`errors`（码 → 枚举错误码，**非空才出现**）、`stale` / `stale_count`（沿用上一拍的值，**非空才出现**）；④ `quote` 字段内的 **`depth`（五档）** 按 AC-A12 的语义出现（有盘口则 20+1 键、无盘口则**无该键**，不得全 0 伪造）；⑤ 帧内 `ts` 非递减（进程内时钟回拨除外）。
  **帧契约口径（只增）**：相对既有帧，本次**只增**字段（`quote.depth` + 上列元信息），不删改既有字段；`errors` / `stale` / `stale_count` 为**条件字段**（空集即不出现），消费方须按「缺省 = 空集」解读。
- **AC-A2【stream.py】顺序性、丢旧保新与发送层去重**：Given 慢客户端队列已满并被丢弃旧帧，When 客户端恢复读取，Then 收到的首帧为最新快照（非中间旧帧），后续帧时间戳严格递增（进程内时钟回拨除外）。**补充两条帧流不变量（v0.6 订正）**：
  - **无连续两帧内容相同**：内容未变的拍**不发帧**（发送层以「去掉 `ts` 后的内容」为去重依据，摘要比对）；**未收到过帧的新连接强制首发**当前帧（不空等一拍；该帧可以是内容未变的重复帧——仅这一次）。**唯一例外**：已被判为慢客户端而丢帧的连接，在其重同步前的窗口不受本保证约束。
  - **不变量订正**：真实不变量是「**轮起点 → 轮起点 ≥ 1 tick**」，**不是**「帧到帧间隔 ≥ 1 tick」。帧在**轮次结束**才发出，到达间隔 = `tick − dur_k + dur_{k+1}`；当上一轮耗时长（如冷轮 3.5s）、下一轮为缓存命中（极短）时可**短于 tick**（实测修复前曾出现 0.535–0.623s 的背靠背帧）。发送层去重后，亚 tick 间隔**只保留给真实数据变化**（新信息立即下发）。

**ACC-2 缓存一致（TTL 分层正确，SCN-1/SCN-3）**

- **AC-A3【stock_api.py】分层新鲜度对齐（白盒断言）**：Given 交易时段（`quote` 域 **L0=4s**），When 验证 REST 批量接口与 SSE 推送的数据来源——取 REST `/stock/basic_info` 与 SSE `quote` 字段这一对（二者共用同一 handler `handle_cls_basic_infos`），Then 白盒断言两路来自**同一缓存层**：同一 handler、同一去重池（`_basic_info_pool`）、同一 `fetch_json` 入口（`fetch_cls_basic_info`），且缓存有效期由同一 Tier 常量派生（R12 修复后对齐至 ≤ 该域分层周期，R16 联动）；辅以值比对：连续采样 60 次（每次间隔 10s），同一股票同一字段经两路读取的值 diff 率 = 0。**判定阈值口径改为「≤ 分层周期和」，取代原「两路时间戳差 ≤ 10s」**（REST 批量响应体无时间戳字段，原阈值无测量基准）：**v0.6 由 8s 口径订正为 4s 口径**——`quote` 域 Tier 已降至 L0=4s，故**预算 = L0 + L0 = 8s**，单路绝对陈旧度 ≤ L0×(1+抖动 20%) ≈ 4.8s；两路同源时差值恒为 0，白盒保证该 8s 预算上限不可触及。该断言消除 R12 描述的 120s vs 分层周期断崖（机制：个股缓存有效期对齐至 ≤ 该域分层周期，分层常量单一来源派生——详见 §4.4 R12）。**待 P6c 校准**：4s 口径预算的实测（原 16s 预算为 8s 口径推导，已随 L0 收紧）。
- **AC-A4【cache.py】无过期脏数据**：Given 某 URL 缓存 TTL=8s 且已过期，When 并发 10 个请求读取，Then 任何响应都不是过期时刻前的旧值（允许 ±0.5s 时钟误差），且过期后至少触发一次回源尝试（回源失败走降级，见 AC-S3）。

**ACC-3 错误语义明确（不误导，SCN-5）**

- **AC-A5【server.py】错误语义表（情形 × 端点适用矩阵）**：Given 依次构造五类情形——参数缺失、未知路径、过载、上游失败、CDP 不可用，When 分别请求，Then 返回严格区分、互不混用，且响应体不伪装成有效数据。**适用矩阵如下（「适用」= 该情形在该端点类别上可复现；矩阵覆盖全部端点类别，逐格断言）：**

| 情形 | 适用端点类别 | 期望响应（HTTP / 体） |
|------|-------------|---------------------|
| 参数缺失 | 带必填查询参数的端点：`/cls/plate`（缺 `code`）、`/stock/*` 全部 6 个（缺 `?code=` 或值为空） | HTTP 400 + `{"error": "<说明>"}`（单体与批量一致，**非**逐码 null） |
| 未知路径 | 任意未注册路径（含拼写错误的 `/stock/xxx`） | HTTP 404 + 文本说明 |
| 过载 | 全部端点（主端口 inflight 达上限；流端口连接数达上限） | 主端口：HTTP 503 立即拒绝不排队；流端口：连接建立被拒（503） |
| 上游失败 | 取数端点——批量 6 个 `/stock/*`；单体 `/cls/hotplate`、`/cls/plate`、`/ths/longhu`；`/market/margin`（**既有 `_error` 形态，单列**）；5 个 RSS 端点 | HTTP 200；批量端点：逐码值 `null` ∧ `_errors[code] = upstream_timeout`/`upstream_error`；单体 `/cls/hotplate`（分区）、`/cls/plate`、`/ths/longhu`：error 客体；**`/market/margin`：既有数据客体内 `_error` 字段**（`{"latest": {…}, "recent": [], "_error": "upstream_timeout"\|"upstream_error"}`，保持 🟠 STABLE 字段集合不变，**不**改为顶层 error 客体）；RSS：降级 feed 内容 |
| CDP 不可用 | CDP 依赖端点——面板 4 个（`/finance/market`、`/finance/timeline`、`/quotation/market`、`/market/timeline`）；批量 1 个（`/stock/f10`） | HTTP 200；面板端点：error 客体（error 字符串不变量）；批量 `/stock/f10`：逐码值 `null` ∧ `_errors[code] = cdp_unavailable`（**非** error 客体，见 AC-S4 A′） |

**「HTTP 状态码」口径（钉死 · v0.5，防再次漂移）**：端点**业务降级一律维持 HTTP 200**（上游失败 / CDP 不可用），失败语义**只由响应体承载**（error 客体 / 数据客体内 `_error` / 逐码 `null` + `_errors`）。状态码仅表达**协议层**结果，四类互不混用：

| 状态码 | 唯一触发条件 | **不得**用于 |
|--------|-------------|-------------|
| 400 | 参数错误——必填参数缺失 / 取值非法 / 无有效股票码 | 上游失败、CDP 不可用、过载 |
| 404 | 未知路径（含拼写错误的 `/stock/xxx`） | 任何业务失败 |
| 503 | **仅**两类：① 准入拒绝（主端口 inflight 达上限；流端口连接数达上限）；② `/healthz` 自身状态为 `degraded` 或健康检查本身失败 | 单体 / 面板 / 批量端点的上游失败或 CDP 不可用 |
| 200 | 其余全部情形（含单体 / 面板业务降级 → error 客体；批量业务降级 → 逐码 `null` + `_errors`；`/market/margin` 降级 → 数据客体内 `_error`） | — |

**依据（编排层裁决，v0.5）**：既有业务系统已在消费旧版接口，上游失败 / CDP 不可用**历史上即为 200 + 结构化错误体**；改为 503 会让按状态码分流的既有消费方把「已带结构化降级数据的正常响应」判为故障（破坏 §7 🟠 STABLE「只增不改」）。故本次**维持 200 不变**。`/healthz` 的 503 是该端点**自身的健康语义**（`degraded`），**不构成**「业务端点降级可返回 503」的先例，不得据此推及其他端点。

**「错误体 vs 值域」边界口径（不混用）**：单体 / 面板端点以 **error 客体**承载失败（**唯一既有例外**：`/market/margin` 以数据客体内 `_error` 字段承载，仍属「单体失败」语义、**非**逐码值域）；批量 `/stock/*` 端点以**逐码 `null` + `_errors`** 承载失败。同一批量响应内**不得**出现顶层 error 客体，反之单体响应内**不得**出现逐码值域承载——跨类别即判失配。

**`/market/margin` 失败体口径钉死（既有契约，🟠 STABLE「只增不改」）**：失败时返回**既有数据客体** `{"latest": {…全 0 数值…}, "recent": [], "_error": "upstream_timeout" | "upstream_error"}`，HTTP 200；**不**改为 `{"error": …}`、**不**改为逐码值域。`_error`（单数）是 margin 数据客体的**既有字段**（字段名与类型 `str` 不变，仅取值由自由文本收敛为枚举错误码，收敛明细见 `market_api.md` §3.2 / §10#2），与批量保留键 `_errors`（复数，§7.1）**不同名、不冲突**；无数据（上游 200 但无记录）时**不含** `_error`（无数据 ≠ 失败）。依据：`doc/detailed/market_api.md` §3.2 / §10#1（SAD §3 明令保留 `_error` 语义）——本次由编排层裁决「设计正确 → 回改 PRD」。

**ACC-4 个股批量处理正确（SCN-1/SCN-4）**

- **AC-A6【stock_api.py】批量一对一映射**：Given 请求 50 个码（乱序，含 3 个无效格式码）混合请求，When 调用任一批量个股端点，Then 返回结果 50 条且 key 与请求码一一对应；无效码值为 null；有效码数据与其代码交叉校验一致（无跨码污染）；无静默丢码（全部 50 码都在结果中）。
- **AC-A7【stream.py】去重与池上限正确**：Given 两个组共 150 码、其中 50 码重叠，When 一个 L1 tick 完成刷新，Then 重叠 50 码每码仅回源 1 次（按上游请求计数验证）；且任何时刻去重池 ≤ 2000 码、单组 ≤ 200 码，超限创建 / 增码被拒（400）而非截断。
- **AC-A8【server.py】RSS 不丢不重**：Given 上游单次返回 50 条快讯，When 请求 RSS 端点，Then 生成的 feed 含全部条目且 guid 无重复；连续两次请求间隔 2×TTL 后再次含全部条目（缓存不丢条目）。
- **AC-A9【server.py】批量截断可感知（R4）**：Given 请求 70 个有效码（超过单批上限 50），When 调用任一批量个股端点（`/stock/data` 等 6 个），Then 响应 JSON 的**保留键** `_truncated = true` 且 `_dropped_count = 20`（= 被截断码数），映射体仅含前 50 码数据。**口径钉死（单一口径，与 §7.1 响应包裹定义一致，消除原「无字段（或为 false）」二义）**：请求码数 ≤ 50 时，`_truncated` 与 `_dropped_count` **两个键均不存在**（不得为 `false` / `0`）；请求码数 > 50 时二者**必然同现**（`_truncated=true` ∧ `_dropped_count = 请求码数 − 50`）。客户端可据此感知截断并分批请求。

**ACC-5 失败与无数据可区分（R14）**

- **AC-A10【stock_api.py】失败与 null 可区分（R14 验证）**：Given 同一批量请求内混入三类码——1 个上游持续失败的码、1 个格式非法的码、1 个有效但上游返回无数据的码，When 调用任一批量个股端点，Then 三类码的**值均为 `null`**（既有值域不变，不抛错、不破坏既有消费方）；且仅失败码出现在新增**保留键 `_errors`**（对象：码 → 枚举错误码字符串，值域 `upstream_timeout` / `upstream_error` / `cdp_unavailable`）中，格式非法码与无数据码**不**出现在 `_errors` 中；消费方仅凭响应即可判定「失败」（值 null ∧ 码 ∈ `_errors`）与「无数据」（值 null ∧ 码 ∉ `_errors`）——即失败 ≠ 裸 null。保留键命名与包裹形状见 §7.1（下划线前缀隔离股票代码命名空间）；该键仅新增、不删改既有字段（§7 🟠 STABLE）。

**ACC-6 数据可用性（北交所 / 空壳防御）**

- **AC-A11【stock_api.py】北交所行情可用性与空壳防御**：Given 请求北交所标的（如 `bj430047` 诺思兰德 / `bj832000` 安徽凤凰）与沪 / 深标的作对照，When 调用带行情的批量端点（`/stock/basic_info`）并订阅 SSE `quote`，Then ① **北交所标的的价格 / 涨跌 / 五档与沪 / 深同等地可获取**（名称、最新价、涨跌、五档均为真实值，非全 null）；② **空壳不得被当作有效数据**——当上游以「HTTP 200 + 键齐但**关键字段全 null**」或空载荷回应（错误格式 / 无效码，如 `bj999999`、`sz999999`），Then 该码必须按**取数失败**处理（值 `null` ∧ 出现在 `_errors`，错误码 ∈ 枚举），**不得**作为成功行情返回、也**不得**写入缓存；③ 沪 / 深标的的行情感知无退化（0 个 error 客体、值与修复前一致）。
  **实测（修复后，2026-09-17 容器内）**：6 只北交所标的（`bj430047` / `bj832000` / `bj831305` / `bj835185` / `bj873169` / `bj920819`）REST 与 SSE 均返回真实行情 + 五档（21 字段、非全 0）；沪 / 深对照（`sh600519` / `sz000001`）无退化；`bj999999` / `sz999999` 走失败语义。**待盘内终验**：北交所标的在**交易时段**的连续多拍刷新（本次样本为盘中单次采样 + 盘后 SSE 帧）。
  **实现约束（内部口径，供实现核对，非对外契约）**：上游对不同市场接受**不同的代码书写形式**（北交所要求点号形、沪 / 深要求前缀形），且**以「200 + 空壳」而非错误码表达书写形式错误**；两种书写形式的转换须有**唯一权威入口**，内部身份键（去重池 / 缓存 / 冷却账本）**不得分叉**。
  **编号理由**：原 AC 体系把「失败 / 无数据可区分」写在 AC-A10（值域语义），但**未覆盖「上游以成功状态码返回不可用载荷」这一类**——它是**数据正确性**（而非降级可用性）问题，且实测已造成过「整市场行情全空」的静默错误，故在「准确」序列**追加** AC-A11。

**ACC-7 五档盘口（depth，能力新增）**

- **AC-A12【stock_api.py / stream.py】五档语义与并入正确（对标 Level-1 券商 APP 的「价格 + 五档」）**：Given 订阅含 `quote` 字段，When 接收帧，Then ① **有盘口的标的**（沪 / 深 / 北交所常规个股）在 `items[code].quote` 内携带 `depth`，含 20 个档位字段（`b_px_1..5`、`b_amount_1..5`、`s_px_1..5`、`s_amount_1..5`）+ `preclose_px`，且**不得为全 0**（全 0 ⇒ 视为无盘口，**不得下发该键**）；② **无盘口 / 取数失败 ⇒ `depth` 键不存在**（**不得伪造全 0 档**），且**不得影响同码 `quote` 本体**（五档是附加数据，缺五档 ≠ 行情失败）；③ 五档刷新与 `quote` **同拍**（同一订阅节拍内真刷新，不落后于价格）；④ 无 `depth` 键的码**不因此**进入 `missing` / `errors`。
  **无 `depth` 键的判定域（须逐类覆盖）**：指数等**无订单簿标的**；无效 / 未知码或上游返回**空载荷**；五档**取数失败 / 超时**；上游**未提供盘口**的其他情形（如新股上市首日、个别标的当日无档位）。**注意**：北交所标的在行情可用时**应携带五档**（见 AC-A11），「无 `depth` 键」≠「北交所不可用」。
  **实测（2026-09-17 盘中）**：50 码 `quote` 组 **50/50 码**携带 `depth`、无全 0 假档（`zero_only=[]`）；指数 `sh000001` 与无盘口标的**无 `depth` 键**；北交所修复后 6 只均携带五档。单帧成本：`depth` ≈ 322 B/码，50 码帧增量 ≈ 16.1 KB（占 `quote` 帧 ≈27%）。**待盘内终验**：连续多拍下五档与价格的**同拍一致性**（本次为单窗口采样）。
  **帧与契约联动**：字段为**新增**（🟠 STABLE「只增不改」）；空值语义为「**键不存在**」（非 `null` 值键）——消费方须按「无键 = 无盘口」解读，**不得**把缺键渲染为 0 档（见 §5 误解 #10）。
  **编号理由**：五档是**新增对外字段**且其「有 / 无 / 真伪」语义与 AC-A1 的帧完整性（覆盖与顺序）**正交**——帧完整性管「码与字段不丢」，本 AC 管「盘口不得伪造、缺失不得误报失败」。故独立成条而非并入 AC-A1。

**ACC-8 RSS 响应缓存校验与条件响应（带宽 / 向后兼容，v0.7 新增）**

- **AC-A13【server.py / cache.py / utils.py】RSS 条件请求（弱 `ETag` / `Last-Modified` / `304` / `<ttl>`）**：Given 5 个 RSS feed 端点（`ROUTES`）已按 TTL 生成 200 响应，When 下游以不同条件头组合重复请求，Then：
  ① **内容未变 ⇒ `304 Not Modified` 且零 body**——**两个校验器通道对等**：`If-None-Match` 命中 **或** 仅 `If-Modified-Since` 满足（内容未变跨 TTL 重生成后 `Last-Modified` 不前进，见 ②）⇒ 304；304 **无 body、无 `Content-Encoding`**、无 `Content-Length`、无 `Content-Type`，**必带**当前弱 `ETag` + `Last-Modified`（有缓存条目时）+ `Cache-Control`（**与 200 同值**）+ `Vary`；客户端复用本地副本（带宽目标：该次 body **由 ~37–45KB 量级 → 0**，见 §3.1 EFF-6）；
  ② **200 必带弱 `ETag`**：形如 `W/"<sha256>"`，派生自**规范化后**的 feed XML——即剔除 `<lastBuildDate>`、`<ttl>`、**`<pubDate>`** 三项**派生元数据**的**内容**后对整串哈希。**双向不变式**：除这三项外的内容未变 ⇒ ETag **不变**（不得因 TTL 重生成换标签而永远 200）；除这三项外任一字节变化 ⇒ ETag **必不同**（不得返回过期副本）。有缓存条目时 200 **另带** `Last-Modified`；
  **`Last-Modified` 语义（v0.8 / F1 修正，取代 v0.7「缓存写入时刻」）**：`Last-Modified` = **表示最后一次变更的时刻**——feed 缓存条目按**指纹**（规范化摘要，与 `ETag` 同源）跨 TTL **继承**：TTL 到期回源重生成时，若重生成字节**未变** ⇒ **继承**上一条目的 `last_modified`（**不前进**，即使上一条目已过期也参与比较）；字节**真变** ⇒ 取本次写入时刻。**不变式（可断言契约）**：在「同一键存在上一条目」的路径上，**`ETag` 变 ⟺ `Last-Modified` 前进**（二者同源于同一指纹）。无上一条目（**首次**请求 / 条目被 LRU 淘汰 / 已被清扫）⇒ `Last-Modified` = 本次写入时刻（**退化为一次性 200 后恢复 304，属可接受降级**）；降级 feed（回源失败）**不发** `Last-Modified`（`If-Modified-Since` 不可评估，**绝不拿陈旧条目的时间冒充降级体**）；**成功表示恒带完整校验器**——写入时即取得本次表示的时间并直接用于本次响应，**消除「200 带 `ETag` 却不带 `Last-Modified`」的窗口**（v0.8 / F5）；
  ③ **条件头语义正确**：`If-None-Match` **优先**——只要它**存在**，就**只**评估它（匹配 ⇒ 304；不匹配 ⇒ 200），**完全忽略** `If-Modified-Since`；支持 `*` / 逗号多值 / 弱比较（**只认字面大写 `W/`**，小写按字面比较 ⇒ 200）；仅 `If-Modified-Since` 时按秒级比较（`Last-Modified ≤ 请求值` ⇒ 304）；**非法 / 不可解析日期头一律忽略 ⇒ 200，绝不 400 / 500**；**跨 TTL 验收（受控时钟）**：内容未变时跨一次 TTL **重生成** ⇒ `Last-Modified` **不前进** 且返回 **304**；内容真变 ⇒ `ETag` 与 `Last-Modified` **两者都前进** ⇒ 200 完整体；
  ④ **`<ttl>` 为 advisory（缓存提示、非时效保证）**：feed XML 新增 channel 级 `<ttl>`（分钟），取值**盘中 30s → `1` / 非盘 180s → `3`**，**最小 1 分钟**（RSS 2.0 只能表达整分钟，不得输出 `<ttl>0</ttl>`）；下游**不得**把 `<ttl>` 当作服务端时效承诺，**需要 <60s 的新鲜度须用 SSE（4s）**；推荐下游轮询 = 「`ETag` 条件请求优先、间隔 ≥30s」；
  ⑤ **向后兼容（无迁移）**：**不带任何条件头**的客户端，其 200 的**状态码、body 与既有响应头逐字不变**（`ETag` / `Last-Modified` 为**纯新增**响应头；`304` 仅在客户端带匹配校验器时出现，属**显式 opt-in**）；既有 `Vary` / `private` 反缓存投毒语义、业务降级恒 200（降级 feed **不发** `Last-Modified`，IMS 不生效）全部保持；
  ⑥ **职责边界与范围（勿混淆）**：**缓存 TTL 管上游新鲜度**——`feed` TTL（盘中 30s / 非盘 180s）到期**仍回源**重生成；**`ETag` 管客户端带宽**——省的是 **body**，**不是**上游请求。**范围**仅 `ROUTES` 的 5 个 feed 的 `GET` / `HEAD`；`/opml.xml`、`/`、JSON 端点**不支持**条件请求（带条件头恒 200、无 `ETag`）；服务端**仍为拉模型**（HTTP/1.0、未启用 keep-alive，304 由 EOF 收尾）。
   **实测与证据（2026-09-18）**：单元侧 **19 条编号（`SRV-T46`–`SRV-T62`，含 `SRV-T52b` 5 方法受控时钟红 / 绿双向）+ `T-CACHE-32` → 24 个测试方法全绿**，全量 **491 OK**（本轮回写前基线 467）；「跨 TTL 内容未变 ⇒ ETag 不变」由纯函数断言 + 三 feed（eastmoney / ths / jin10）handler 受控时钟断言 + 端到端 `304` 共同钉死；部署路径含 200 / `Content-Length` 与 304 实测（详见 `doc/tester/RSS条件请求_测试执行报告.md`、`doc/tester/integration-report.md`）。
   **v0.8 / F1–F7 追加证据**：`SRV-T63`（**IMS 跨 TTL 304，F1 决定性**）、`SRV-T64`（指纹继承 / 变更两向）、`SRV-T65`（**跨 Host 键隔离，F2**）、`SRV-T66`（`http_304_total`，F3）、`SRV-T67`（304 头集合白名单，F6）、`SRV-T69`（`_feed_ttl_minutes()` ↔ max-age，F4）、`SRV-T70`（`feed_cache_put` 返回值 / miss 无二次查询，F5）；`T-CACHE-33/34` + `MET-T18`；**全量 504 OK**（详设 `server.md` v1.9 §8 计数 64 → 72）。**说明（v0.10 加注）**：本段 `491` / `504` 均为**v0.7 / v0.8 分轮时点快照**；**现行以最新口径为准**——见 §1 / §9：**514 单元用例全绿**（集成 `25/25` + `7/7`）；详设**设计编号 75 条** ↔ 实测 **514 方法**（二者不同量）。
   **取舍与优先级（v0.8 更新；须同步 `API.md`）**：
   - **【已修复，取代 v0.7「已知取舍②」】** v0.7 曾登记「`Last-Modified` = **缓存写入时刻** ⇒ **仅带 `If-Modified-Since`** 的客户端跨 TTL 边界仍得 200 全量」。**P8 F1 已修复**：`Last-Modified` 改为**表示最后一次变更的时刻**（指纹跨 TTL 继承，见 ②），IMS-only 客户端在**内容未变**时跨 TTL 重生成**同样得 304**——**不再作为已知取舍**。
   - **【被否决备选（决策记录，体现「准确 > 高效」）】** `Last-Modified = max(items 的 `pubDate`)`：**免状态**、实现更简，但上游「**改描述不改 `pubDate`**」（同一 `<guid>`、title / description 已变而 `pubDate` 未动）时会发出**错误 `304`（下游持续持陈旧数据）**。**对交易数据服务，错误 304 远比多发 200 严重**（多发 200 只损失带宽，错误 304 会把「数据已变」静默判为「未变」）⇒ **否决**，改用**需要状态**的指纹继承方案。**同理**：`ETag` 的规范化投影以「**不误 304**（内容真变必换标签）」为不可妥协项，即使这会牺牲部分「不误 200」的保守性（由 `pubDate` / `lastBuildDate` / `<ttl>` 三项剔除承担）。
   - **【仍保留的取舍（可接受）】** 仅 `<pubDate>` 字节变化（上游真实更正发布时间）⇒ `ETag` 不变、`Last-Modified` 亦**不前进**，下游最多持旧副本至下一次真内容变化 / TTL 重生成（item 身份仍由 `<guid>` 承载）。
  **编号理由**：本能力是**既有端点的外向响应语义承诺**（新增响应头 / 新状态码 / feed XML 新元素），其可观察面首先是「**响应正确性**」——304 只在内容未变时出现（不得误 200 / 不得误 304）、条件头非法不得报错、无条件下行为不得变化；带宽收益是**结果**而非判据（条件请求 ≠ `Cache-Control: max-age`，后者只表达「客户端可复用多久」，不解决「到期后内容未变仍需重传 body」，二者互补）。故与 AC-A5（错误语义）、AC-A8（RSS 不丢不重）同属**「准确」序列**，追加为 **AC-A13**（**沿用 SAD v1.8 §2.7 / ADR-023 已声明的追溯号**；追加编号、不重排既有编号）。RSS 端锁定 **🟠 STABLE**（严格「只增不改」）。

**ACC-9 表示维度完整性（缓存键覆盖，安全属性，v0.8 新增）**

- **AC-A14【server.py / cache.py】feed 缓存键覆盖表示的全部变化维度（防跨 Host 串号 / 订阅链接劫持）**：Given 5 个 RSS feed 端点在 `PUBLIC_BASE_URL` **未设** / **已设**两种配置下运行，When 以不同 `Host` 请求同一 feed，Then：
  ① **`PUBLIC_BASE_URL` 已设 ⇒ 缓存键与请求 `Host` 无关**（同一 feed 恒一把键、同一条目），响应体 `<atom:link rel=self>` 恒由配置的 `PUBLIC_BASE_URL` 决定；
  ② **`PUBLIC_BASE_URL` 未设 ⇒ 缓存键必须覆盖 `base_url`**（键 = `path` + 分隔 + `base_url`；`base_url` 由请求 `Host` 派生）——**不同 `Host` 的响应互不串号**：对同一 feed 先后以两个不同 `Host`（如 `a.example` / `b.example`）请求，**各自**拿到指向**自身** `Host` 的 `<atom:link rel=self>`，**后者看不到前者的链接**（缓存内两条独立条目），且后者**不因命中前者条目**而返回错误链接；
  ③ **安全属性（本条同时是非功能安全要求）**：该键隔离防止「**一条伪造 `Host` 的请求在一个 TTL 内改写该 feed 全部下游读者的订阅链接**」（link hijack），并使 `Vary: Host, X-Forwarded-Host, X-Forwarded-Proto` 的**头承诺与源站缓存行为一致**（此前头承诺跨 Host 隔离、源站却按 `path` 串号，属**虚假隔离**）；非法 / 畸形 `Host` 经统一校验塌缩为**单一** `localhost:PORT` 键（不能靠畸形 Host 枚举放大条目）；
  ④ **防击穿按同一键隔离**：同一 feed 的并发请求按**同一缓存键**建锁（不同 `Host` 各自独立），双检命中内容与该 `Host` 的表示一致。
  **边界（勿误读）**：`PUBLIC_BASE_URL` 已设时键恒为 `path`（此时表示本就与 Host 无关），**不是**「任何情况下键都忽略 Host」；未设时才含 `base_url`。键对 `cache.py` 为**不透明字符串**（cache 层不引入 `Host` / `PUBLIC_BASE_URL` 概念）。
   **编号理由**：本 AC 与 AC-A13 同属 RSS 响应语义但**正交**——AC-A13 管「**同一表示**的条件命中（304 / `ETag` / `Last-Modified`）」，本 AC 管「**不同表示不得共用缓存条目**（键隔离）」；且本条首要是**安全属性**（防跨 Host 订阅链接改写），非纯带宽 / 正确性，故独立成条，在「准确」序列追加为 **AC-A14**（沿用 **BR-SRV-45**；追加编号、不重排既有编号）。RSS 端锁定 **🟠 STABLE**（严格「只增不改」）。
   **取舍与优先级（v0.9 追加；本轮暴露模式，须记录）**：
   - **模式：「修复一个安全 / 正确性问题时，必须同时论证它引入的资源界」**。F2 本身**正确且必要**——它修好了**订阅链接劫持**（一条伪造 `Host` 在一个 TTL 内改写全部读者订阅链接），把键空间从「5 条固定 `path`」扩为「`path` × 请求派生 `base_url`」；但**扩容的键空间本身是新的资源面**，而 `_valid_host_header` **只校验格式、不校验归属** ⇒ **合法**主机名即可枚举出无限键。**BR-SRV-45 的原「放大风险论证」只覆盖了上游请求**（键增多不放大上游 —— 被 URL 级缓存兜住），**未覆盖锁表内存与本地 XML 生成**；后果是进程内内存无界增长（每键 ~300–450 B）+ 缓存超上限后每请求本地重生成 XML。
   - **裁定与优先级（稳定 ≥ 高效）**：该资源界由 **F8 补齐**（锁表引用计数 + 归零回收，规模收敛于「并发在飞的键数」——见 **AC-S12** / **BR-SRV-50** / **BR-CACHE-35**）。**代价如实记录**：本可**零成本**继续沿用「永不回收锁」以避免 TS-4 双抓复现，但那是**以无界内存换实现省事**；本 PRD 采纳「**稳定 ≥ 高效**」——宁可多一层引用计数与 `try … finally` 纪律，也不接受**外部可触发**的进程内无界增长。**不得**退化为「取锁即删」（会让「已取锁未进临界区」的线程与后来者拿到两把锁 ⇒ 同键双抓）。
   - **可观测后果**：本条**无对外字段 / 头项变化**（纯内部资源界），故不进入 `API.md` 同步面；其可验收面全在 **AC-S12**。

### 3.3 稳定（Stability）

**STB-1 无崩溃 / 死锁 / 异常不扩散**

- **AC-S1【server.py】全端点异常兜底**：Given 逐个端点注入异常（上游超时、非法响应、CDP 页面无数据），When 请求每个端点，Then 均返回结构化 error 客体或正常关闭连接，进程存活、无未捕获异常日志冒泡；其余端点 5s 内功能不受影响。
- **AC-S2【stream.py】并发修改不中断推送**：Given 推送循环运行中，When 并发对同一组执行 500 次增删码（PATCH），Then 无任何 tick 因并发异常中断（日志无迭代中断类错误），且 tick 间隔劣化 ≤ 20%（相对无并发基线）。
- **AC-S6【stock_api.py】单码故障不扩散（降级值精确定义）**：Given 上游对某 1 个码持续失败、其余 49 码正常，When 批量请求 50 码，Then 49 码正常返回数据客体；失败码的**降级值 = `null`**（保留 API.md 既有「null = 无数据」含义，**不改写既有值域**），同时在该响应的**新增保留键 `_errors`** 中给出该码的**枚举错误码字符串**（值域 `upstream_timeout` / `upstream_error` / `cdp_unavailable`，不允许自由文本）；判别式：值 null 且该码 ∈ `_errors` ⇒ 取数失败；值 null 且该码 ∉ `_errors` ⇒ 无数据 / 无效码——故「失败」与「null 无数据」可区分。批处理不被阻塞；同码连续失败 3 次后进入冷却期（120s），冷却期内该码不回源（按上游请求计数验证）。

**冷却账本记账口径（钉死 · v0.5）**：冷却账本**只统计「真实上游失败」**——即经网络尝试并失败、归类为枚举错误码（`upstream_timeout` / `upstream_error` / `cdp_unavailable`）的取数失败（同一 `(域, 码)` 连续 3 次 ⇒ 120s 冷却）。**本地预算耗尽不计入冷却账本**：当批量整体期限（我方 deadline）已过、未发起任何网络请求时，客户端**仍可见** `upstream_timeout`（错误码对外形态不变，消费方无须区分），但该次失败**不写入冷却账本、不累加失败计数、不缩短也不延长任何冷却窗口**。**依据（编排层裁决，v0.5，正式反转 REV-DES-15 裁决②）**：本地预算耗尽属**系统自造超时**（我方期限已到），**非上游故障**；若计入，一次慢批会把整批尾部码统一打进 120s 停更，造成**自我放大**（越多的码被冷却 ⇒ 下一轮可用预算越少 ⇒ 更多本地超时 ⇒ 更大范围冷却）。判别口径：**上游故障（记账）** = 存在网络尝试且失败；**本地预算耗尽（不记账）** = 无网络尝试、我方期限已过（对外仍报 `upstream_timeout`）。验证方式：注入「永不返回」上游使批量期限耗尽，Then 断言 `code_cooldown_list` 中该批码**保持为空**（按冷却清单快照验证），且后续批次仍对这些码发起网络尝试（按上游请求计数验证）。

**STB-2 优雅降级（上游超时 / CDP 不可用）**

- **AC-S3【cache.py】上游全挂有界响应（故障注入模式钉死）**：Given 全部上游被**故障注入**为不可用，**注入模式钉死为两种，各自单独跑一轮、单独断言**：
  - **模式 A「连接秒拒」**：TCP connect 立即被拒（RST / ECONNREFUSED，服务端口关闭或 refuse 策略）——Then 请求应**快速失败并走降级**（负缓存 / error 客体 / 批量逐码 `null`+`_errors`），端到端 P95 ≤ 1s（不消耗超时预算），不得因「无适配的立即失败路径」而等待满超时。
  - **模式 B「黑洞超时」**：连接建立成功但**永不返回响应**（数据黑洞，accept 后静默），单次注入持续 60s——Then 命中各层超时兜底，单请求阻塞时长 ≤ 15s（含回源等待与降级等待），端到端 P95 **按请求密度分档**：**高请求密度下 P95 ≤ 5s**；**低请求密度下 P95 ≤ 10s**；**任何单请求 ≤ 15s**（不变）。
  - **模式 B 的 P95 口径前提（前提不成立则本档目标需重标，不可直接引用）**：探测预算阶梯**封顶 5s**（2s → 4s → 5s，**不再升到 `REQUEST_TIMEOUT`**）+ 负缓存 `NEG_TTL = 5s`。稳态推导：持续黑洞下同一 URL 的两次探测间隔 ≈ `5s 探测超时 + 5s NEG_TTL` = **10s 周期**；周期内「命中未过期负缓存 → 立即结构化降级」的请求耗时 ≈ 0（不计入慢尾），「撞上探测窗口 → 等满 5s 探测预算」的请求耗时 ≈ 5s，慢请求占比 ≈ 50% ⇒ **高密度下 P95 ≈ 5s**（高密度时请求到达近似均匀，必然采样到探测窗口）；低密度下单位时间请求少、多数请求落在已写入的负缓存内，P95 退化为**周期上界 ≈ 10s**（`5s 探测 + 5s NEG_TTL`）。**任一分量变动（探测阶梯封顶值 / `NEG_TTL`）必须同步重标本 AC 并在 §9 更新待校准项**——本档 P95 不是与预算无关的绝对承诺。

  When 在两种模式下**分别**持续请求全部 REST 端点 5min，Then 均满足：100% 请求有响应（结构化 error 客体 / 批量端点逐码 `null` + `_errors` / 缓存数据，**绝不 500、绝不裸断连**），且任一请求处理线程阻塞时长 ≤ 15s。两种模式不得合并为一次注入（「秒拒」与「黑洞」触发的降级路径不同，合并会掩盖未适配的立即失败分支）。**模式 B 另需按请求密度分两轮**分别采集 P95 并按上表断言（**高密度** = 持续施压、请求到达间隔 ≪ 10s 探测周期；**低密度** = 串行请求、间隔 > 1 个探测周期），两档不得合并为一次采集（合并会被高密度样本覆盖，掩盖低密度档的真实 P95）。
- **AC-S4【cdp_engine.py】CDP 降级路径**：Given Chrome 停止（CDP 不可用），When 逐端点请求，Then 按「CDP 依赖度 × 端点形状（单体/面板 vs 批量）」四分处理（清单以只读核对 server.py 路由表 + 实现为准，逐项确认无遗漏）：

**3.3.1 可观测性（稳定前置条件，S 级）**

- **AC-S10【全模块】关键指标可观测**：Given 正常运行，When 查询健康状态或日志，Then 可观测到：各 tick 实际耗时与滑动次数、503 计数、**304 计数（`http_304_total`，v0.8 / F3 新增）**、SSE 队列丢弃帧计数、各缓存条目数、上游失败码冷却清单、CDP 重启窗口状态。仅用标准库日志与现有接口实现，不引入监控依赖。
  **304 计数口径（v0.8 / F3；「省带宽」必须可观测）**：`http_304_total` 在 **304 响应处单点计数**（任何 304 都被计入、不可能漏记），**单调递增**；200 **不增**；从未发生 304 时读到 **`0`**（零值恒定发布，**非键缺失**）。**该计数只需计数、无需分母**——若「**派生元数据抖动 ⇒ 永远 200**」的回归发生，计数**停止增长本身就是报警信号**（一个既不增长、又无分母的单调计数即足够，无需 200 分母）；故「省带宽」这一收益在生产**可被验证**（否则无法回答「到底省了多少」、也无法在回归时发现 304 命中骤降）。
- **AC-S11【stream.py】断线重连并续帧**：Given P2 客户端已订阅某组且正常收帧，When 客户端断开并在 1 个 tick（`quote` 组 **L0=4s** 口径；仅慢域组 8s）内以同 sid 重连，Then 重连在 ≤ 1 tick 内成功建立 SSE 并收到下一 tick 的完整快照帧（不要求补发断线期间的帧，丢旧保新语义与 AC-A2 一致；重连属「未收到过帧的新连接」⇒ 按 AC-A2 强制首发，不空等一格）；若重连晚于组空闲回收期（300s）或组已被回收，则客户端经重新 POST 建组后同样在 ≤ 1 tick 内收帧。
- **AC-S12【server.py / cache.py】feed 取数锁表随并发收敛（per-key 资源有界，v0.9 新增）**：Given 5 个 RSS feed 端点运行、`PUBLIC_BASE_URL` **未设**（键含请求派生 `base_url`，键空间可被**合法**主机名枚举），When 对**同一** feed 以 N 个不同 `Host` 依次（**串行**，每次请求完成后才发下一个）请求，Then：
  ① **锁表规模不随 N 增长**——第 1 次与第 N 次（N=50）请求完成后的锁表条目数**同样为 0**（稳态无在飞时**归零**），**不得**为 `N`；**并发变体**：K 个不同 Host 同时在飞时条目数 **≤ K**，全部返回后**归零**；
  ② **异常路径同样回收**——`fetch_func()` 或缓存写入抛异常时，该键的引用计数**归零且键被回收**（`try … finally` 释放纪律，不得因异常泄漏计数而使锁表退化回只增不减）；
  ③ **并发同键不产生重复取数**——同一键的两个并发请求，`fetch_func` 仅被调用 **1 次**、两响应体相同（双检 + per-键锁不变，既有防击穿前提）；
  ④ **`PUBLIC_BASE_URL` 已设时**键恒为 5 条固定 `path`，锁表规模上界为 **5**（与 Host 无关）。
   **为什么不能退化为「取锁即删」**：若在引用归零前回收键（取锁后立即删，或按 TS-4 旧法在临界区外 `pop`），「**已取出锁但尚未进入临界区**」的线程与后来者会各拿**两把不同的锁** ⇒ **同一键双抓**（正是 `系统_代码评审报告_001.md` TS-4 的历史事故，也是此前**主动移除 `pop`** 的原因）。故必须**引用计数**——不变式是「**只要还有线程持有或即将获取该键的锁，计数 ≥ 1，该键不可能被回收**」，仅当计数归零（无任何持有者 / 等待者）才回收**锁与计数两表**。
   **正确性依据（可在评审会核对）**：回收只发生在计数归零时；随后到达的线程创建新锁，其**双检**仍命中前一持有者已写入的缓存条目 ⇒ **不产生重复取数**（第二次真取数只可能因条目确实已过期）。
   **有界性结论**：锁表规模**收敛于「并发在飞的键数」**，而非「累计见过的键数」；**可选运营缓解（非契约）**：部署侧强制设 `PUBLIC_BASE_URL` ⇒ 即便暂不部署本修复，也无 Host 派生的键空间。
   **编号理由**：本条与 AC-E6（URL 缓存有界）、AC-E7（连接与队列有界）同属「**资源无无限增长**」家族，但既有资源 AC 均管**条目数 / 连接数上限**，**未覆盖「随外部输入可枚举的 per-key 表」这一类**（F2 把键空间从 5 条固定 `path` 变成 `path × 请求派生 base_url` 后新暴露）；且判据是**收敛性（不随累计键数增长）**而非绝对上限，故独立成条、在「稳定」序列追加为 **AC-S12**（沿用 **BR-SRV-50** / **BR-CACHE-35**；**稳定序列已有 AC-S11「断线重连并续帧」，故续编为 S12**；追加编号、不重排既有编号）。RSS 端锁定 **🟠 STABLE**（**对外行为零变化**——纯进程内资源界收紧，`Host` 参与表示与缓存键的界定见 AC-A14）。

| 3 | 「帧完整」时点：新订阅码延迟 1 tick 出现 | 若要求订阅即出现在当前帧 → 需增量帧路径（超出本次范围） | 订阅 / 增码后，下一 tick 起帧完整 |
| 4 | 「上游故障不放大」接受度：负缓存引入故障恢复感知延迟 | 若拒绝负缓存 → 只能靠有界回退，延迟达 13.5s 且上游压力大 | 接受失败短缓存（≤5s）+ 有界回退并发（已存在） |
| 5 | 盘中 CDP 守护重启是否可跳过 | 若盘中必须重启 → 45s 无数据窗口无法消除，AC-S4 目标需放宽 | 待决策：交易时段跳过守护重启（倾向），非交易时段照常 |
| 6 | **「业务失败 ⇒ 5xx」是最常见的错误直觉**（AC-A5） | 若把上游失败 / CDP 不可用改成 503，按状态码分流的既有业务系统会把它判为故障 → 既有消费方断裂，需回滚 + 契约审计返工 | **维持 200**：业务降级只由响应体承载（error 客体 / 数据客体内 `_error` / 逐码 `null` + `_errors`）；503 仅准入拒绝与 `/healthz` degraded（§3.2 AC-A5 状态码口径表） |
| 7 | **「超时都是失败、失败都该记冷却」**（AC-S6） | 若本地预算耗尽也记冷却 → 一次慢批把整批尾部码打入 120s 停更，**自我放大**（冷却越多 ⇒ 预算越少 ⇒ 更多本地超时），故障恢复期被无谓拉长 | **区分两类失败**：真实上游失败（有网络尝试）才记账；本地预算耗尽（无网络尝试，我方期限已过）对外仍报 `upstream_timeout` 但**不进冷却账本**（§3.3 AC-S6） |
| 8 | **「SSE 节拍 = 全局 L1=8s」**（AC-E10） | 若按 8s 验收 → 会把已实现的 L0=4s 判为超标；反之只按 4s 验收 3 域组，会把「按域分拍」的慢域刷新（8s）判为失败 → 延迟目标与实测互相打架 | 节拍 = **订阅域最短 TTL**：`quote` 组 4s、3 域混合组 4s（`quote` 每拍真刷新，慢域每 2 拍 = 8s）；端到端目标 **`quote` 50 码 ≤4s / 3 域 50 码 ≤8s**（§3.1 AC-E10） |
| 9 | **「帧间隔必然 ≥ 1 tick」**（AC-A2） | 若按此断言 → 冷轮（长）→温轮（短）会自然产生亚 tick 间隔，测试会误判为回归；而真实不变量「轮起点 ≥1 tick」反被漏测 | 不变量 = **轮起点 → 轮起点 ≥ 1 tick**；亚 tick 间隔**只允许**出现在「真实数据变化」的情形（内容未变则不发帧）——见 §3.2 AC-A2 |
| 10 | **「`depth` 缺失 = 数据缺失，应补 0 档」**（AC-A12） | 若把无 `depth` 键补成全 0 档 → 客户端把「无盘口」渲染成「买卖盘全 0 元」，属**伪造行情**（比缺字段更危险）；若把无 `depth` 计入 `missing` → 指数 / 北交所被误报为行情失败 | **无键 = 无盘口**（不补 0、不计入 `missing`）；全 0 档视为无盘口且**不下发该键**；五档缺失**不影响** `quote` 本体（§3.2 AC-A12） |
| 11 | **「上游返回 200 就是有数据」**（AC-A11） | 若只信状态码 / `code:200` → 错误格式或无效码的**全 null 空壳**会被缓存并推给客户端，整市场行情静默变空（北交所曾全空且无任何错误信号） | 须做**关键字段非空校验**（空壳防御）：空壳 / 无效载荷一律按**取数失败**处理（值 `null` ∧ ∈ `_errors`），不得缓存、不得当有效数据（§3.2 AC-A11） |
| 12 | **「`<ttl>1</ttl>` = 服务端承诺 1 分钟时效」**；以及**「条件请求省的是上游回源」**（AC-A13） | 若把 `<ttl>` 当时效保证 → 聚合器照抄把轮询放慢到 60s，**比服务端 `Cache-Control: max-age=30` 更慢**，需 <60s 时效的场景会拿到过期快讯；若以为 `ETag` 能省上游请求 → TTL 到期仍回源，容量模型与上游负载预期会被误判 | **`<ttl>` 是 advisory 缓存提示、非时效保证**（最小 1 分钟，RSS 2.0 只能整分钟）；推荐「`ETag` 条件请求优先、间隔 ≥30s」，**需 <60s 用 SSE（4s）**；**职责边界**：缓存 TTL 管上游新鲜度（到期仍回源），`ETag` 管客户端带宽（省 body 不省回源）。**两个校验器通道对等**：`Last-Modified` 表示最后一次变更时刻，内容未变跨 TTL 重生成不前进 ⇒ **仅带 `If-Modified-Since` 的客户端同样得 304**（v0.8 / F1；旧版「IMS-only 跨 TTL 必 200」已修复，见 §3.2 AC-A13） |
| 13 | **「feed 缓存键按 `path` 即可」**（AC-A14） | 若键不覆盖表示的全部变化维度 → body 内嵌请求 Host 派生的 `<atom:link rel=self>`，一条伪造 `Host` 请求会在一个 TTL 内改写该 feed **全部**读者的订阅链接（link hijack），且 `Vary` 的头承诺与源站行为不符（虚假隔离） | 键必须覆盖表示全部变化维度：`PUBLIC_BASE_URL` 已设 ⇒ 键 = `path`（与 Host 无关）；**未设 ⇒ 键含 `base_url`**（不同 Host 互不串号）；非法 / 畸形 Host 塌缩为单一 localhost 键（§3.2 AC-A14） |
| 14 | **「`Host` 只是转发头，不影响服务端资源」**（AC-A14 / AC-S12） | 若据此认为任意 `Host` 都无代价 → 忽视 F2 后「`PUBLIC_BASE_URL` 未设 ⇒ 键含请求派生 `base_url`」这一事实：**合法**（不一定畸形的）主机名即可**枚举新键**，使进程内 per-key 表（feed 缓存 / 取数锁表）与本地 XML 生成随请求增长 ⇒ 2C2G 节点内存无界增长（F2 引入、F8 界定的正是这个面） | `Host` 在 `PUBLIC_BASE_URL` **未设**时**参与 feed 表示与缓存键**（已按 F2 界定键维度、按 F8 界定**资源界**）；服务端**不得**因「Host 只是转发头」而放弃对 per-key 资源的收敛要求——per-key 资源必须随**并发**收敛、不随**累计键数**增长（§3.2 AC-A14 / §3.3 AC-S12） |

> 待确认项：以上 #5 的取舍、R4 截断标记是否改动对外契约（影响 §7 同步范围）、MAX_CACHE_SIZE=2000 是否为硬上限（预算内）。

## 6. 明确不做（Out of Scope）

- **不改技术栈**：保持 Python 标准库零第三方依赖（不引入任何库 / 框架）。
- **不做前端 / UI**：本 PRD 只涉及服务端行为，不含任何界面改动。
- **不引入外部存储**：维持无数据库、无 Redis 等外部存储，全部状态在内存。
- **不做协议扩展**：不加 WebSocket / 多协议推送；SSE 全量快照帧机制保持。（v0.6 澄清：发送层**跳过「内容未变」的帧**属既有全量快照机制内的优化——每帧仍是完整快照，**不是**增量 diff 帧。）
- **不做增量 diff 帧**：SSE 帧格式升级（增量推送）记为 W 级备选，本次不实现。（与上条区分：去重只减少**重复全量帧**的发送次数，不改变帧内结构。）
- **不做鉴权 / 多租户**：订阅模型维持匿名组。

**批量端点响应包裹定义（本次新增，先行钉死命名空间）**：`/stock/*` 批量端点的响应是**扁平映射** `{ "<code>": <data|null>, ... }`（既有形状不变，🟠 STABLE）。股票代码键形如 `sh600519` / `sz000001`，**不含前导下划线**。为避免新增元信息键与股票代码键**同命名空间冲突**，本次全部元信息一律放入**下划线前缀保留键**（reserved keys）：
