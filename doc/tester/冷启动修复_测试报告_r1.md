## 4. 连发检查（BUG-冷启动-01，P2）— ❌ 未通过，但**根因不是唤醒机制**

**任务判据**："无 <1 tick（<2s）的背靠背帧"。实测：

| 场景 | 最小帧间隔 | 判定 |
|---|---|---|
| 稳态 quote 50（A 组） | 3.610s | ✅ |
| 并发加订阅 burst 探针 conn1 / conn2 | 3.847s / 3.943s | ✅ |
| 稳态 3 域 50（B 组） | **1.910s** | ❌ |
| 冷启动 3 域（cold4/5/6） | **0.535 / 0.623 / 0.582s** | ❌ |

**根因（非唤醒）**：`_tick_sleep_seconds` 把**轮次起点**钉到整数网格 `t0 + k×tick`，而帧发出时刻是**轮次结束**（`起点 + dur`）。故相邻帧差值

```
间隔 = tick − dur_k + dur_{k+1}
```

只要 `dur_k > tick/2` 而 `dur_{k+1}` 很小（缓存命中），间隔即可远小于 tick，最坏趋近 0。本轮把 3 域 tick 从 8s 降到 **L0=4s**，而 3 域单轮实测 2.2–3.5s（> 4/2），于是**首次进入该区间**；上轮 tick=8 时 `dur≪tick`，间隔恒 ≥5s，故该现象此前不可达。**与唤醒无关**——被唤醒只是把首轮起点从"某个网格点"平移到"建连时刻"，`起点→起点` 仍严格 4s；把首轮起点换成任一网格点，得到的帧间隔完全相同。

**排除"唤醒引入额外轮次"的证据（关键）**：`doc/tester/wake_burst_probe.py --concurrent`（50 码拆 25+25，conn2 在 conn1 之后 1.223s 加入）：
- conn1 帧时刻 0.418, 4.265, 8.217, 12.295, 16.317, 20.263, 24.222；间隔 3.847–4.078（**min 3.847**）。
- conn2 首帧 **4.264s**（= 下一网格点 `0.008+4k` 的广播），**未**在加入后立即拿到帧 → "活跃轮硬睡、pending 延后到网格点"的设计生效，**无越网格帧**。
- 20s 内活跃轮仅 6 个：起点 0.008 → 4.008 → 8.008 → 12.008 → 16.008 → 20.008（帧时刻 = 起点 + dur，逐一对上）；**轮数与帧数 1:1，无额外轮次**。
- `degraded=0 slip=0 lag_max=0`。

**放大效应评估（为何定 P2 而非 P1）**：那次短间隔的第二帧是**缓存命中重复帧**（`dur_{k+1}` ≈ 33–52ms，`upstream_fetch` 无增量），无上游额外负载、无卡顿（无 12–17s 前置停顿）、无数据丢失（`missing/stale=0`），且冷启动场景下"首帧更早、次帧早到"对客户端反而有利。**但它确实证伪了代码与测试中写死的判据**：`stream.py::_tick_sleep_seconds` docstring 与 `tests/test_stream.py::TickThrottleTests` 均声称 *"on the grid the interval is never shorter than one tick"*。真实不变量只是 **起点到起点 ≥ tick**，帧到帧无此保证（现有单测只用 tick=8 / dur=3.0，落在安全区间，故未暴露）。

**建议**（供编排层决策，tester 不改码）：① 修正判据表述为"轮次起点间隔 ≥ tick"；或 ② 若要求帧到帧 ≥ tick，需在轮次结束时补 `min_sleep = tick − dur_k`（或改为按帧发出时刻对齐网格）。

## 5. 空闲→订阅唤醒验证

**判据**：`建连→首帧` 若 ≈ `首轮 tick_ms`（而非"首帧 = 网格等待 + 首轮耗时"），即唤醒生效（否则最坏要多等一个 L1 基线 8s）。

| 证据 | 数值 |
|---|---|
| 6 次冷跑：`conn→首帧 − 首轮 tick_ms` | **+2ms … +5ms**（即残差≈0，无任何网格等待） |
| cold3：conn→首帧 0.954s / 首轮 951.76ms | 残差 2ms |
| 热进程 burst 探针 conn1：首帧 0.418s / 该轮 410.12ms | 残差 ~8ms，且轮起点 0.008 ≈ 建连时刻 |

**结论 ✅ 生效**：进程冷/热皆在订阅变活的瞬间开始 refresh，不再等 8s 基线网格。分两个触发点均被覆盖：`create_group`（建组即探测）与 `_serve_sse`（连接注册后立刻唤醒，`conns.add` 在唤醒之前，故醒来即见活跃需求）。上轮 9.87s 中的 **5.69s 网格等待已消除**。

## 7. 结论

1. **冷启动已修复 ✅**。50 码 quote 冷首帧 0.957–4.259s（上轮 9.87s），50 码 3 域 3.457–3.535s；根因（空闲首订阅等一个 L1 基线网格 = 5.69s）被 `_wake_push_loop` 消除，实测残差 2–7ms；预热传输把冷路径成本留在 0.95–4.26s（quote）/3.39–3.49s（3 域）。
2. **首轮超预算不计 degraded/slip ✅ 生效**（6 次冷跑 Δ=0，含 4254.84ms 的首轮），且"仅一轮 + 空轮不消耗"由单测证明。
3. **稳态无回归 ✅**：quote 间隔 ≈4.05s、3 域首全量 2.17s、`lag=0`、`stale=0`、`missing=0`、`503=0`、`dropped=0`、队列字节 0。
4. **无 P0/P1 阻断项**。**1 项 P2（`BUG-冷启动-01`）**：`dur_k > tick/2` 时帧到帧间隔可 <tick（实测 0.535s / 1.91s），**由 L0=4s 降低 tick 首次使该区间可达，非唤醒机制所致**（轮次起点严格 4s、轮数=帧数、次帧为缓存命中重复帧）；同时证伪 `_tick_sleep_seconds` 及 `TickThrottleTests` 中"帧间隔永不短于一个 tick"的判据表述。
5. **未覆盖/待确认**：① L1=120s **非盘中**唤醒行为未测（本次全程盘中 13:00–15:00）；② 并发多订阅只测了 2 组 25 码，更高并发（≥8 组满配）未压；③ cold1 的 4.259s 紧跟在 `--build` 之后，疑为构建期资源竞争，样本方差大（0.96–4.26s），冷路径成本仍需更多样本或上游侧归因。
