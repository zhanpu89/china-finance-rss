## 5. 关键修复点实测

### 5.1 P0 longhu 席位配对 — ✅ 通过

`/ths/longhu` → 200，`total=64`，`data` 64 行。结构不变量（全 64 行）：

- 每行 `buy_top5` / `sell_top5` **均存在且各 5 条**（缺失 0；`len(buy)!=len(sell)` 0 行）→ 位置配对 `stock_idx=broker_idx//2` 对每只票都成立；
- 每条席位含 `name/buy/sell/net` 四键（缺键 0）；
- `buy_top5` 按 `buy` 降序、`sell_top5` 按 `sell` 降序（不满足者 0 行）→ 两张表各自是自洽的「前5名」表；
- 33/64 行存在同一席位同时出现在买/卖两侧（龙虎榜正常现象，非错位）。

日志：`docker compose logs | grep -iE "\[longhu\]|misalign"` → **无任何 `[longhu]` 告警、无 misaligned**。即 `broker_idx == 2*len(stocks)` 成立，P0 的 `broker_idx += 1` 无条件推进修复**有效**。

### 5.2 canonical 归一（跨批衔接）— ⚠️ 入口对、回写错

**stream 入口（对）**：POST `{"codes":["600519.SH","sh600519"],"fields":["quote"]}` → `{"sid":"...","codes":["sh600519"],...}` → 两种写法折叠为 **1 码**，去重与预算核算正确。

**HTTP 入口（入口对、响应错）**——生产实测：
```
GET /stock/data?code=600519.SH          → 200 {"sh600519": "600519.SH"}      ← 应为该股行情对象
GET /stock/data?code=sh600519           → 200 {"sh600519": {…正常行情…}}      ← 无重拼写，正确
GET /stock/data?code=600519.SH,sh600519 → 200 {"sh600519": "600519.SH"}      ← 去重为1码但 body 错误
```
点号形式请求返回 **HTTP 200 + 垃圾 body**（值为拼写字符串），无任何错误信号。

### 5.3 非 list body — ✅ 通过
`{"codes":123}` → 400 `codes must be a list`（不是连接重置/500）。`fields:["nonsense"]` → 400 `unknown field: nonsense`。

### 5.4 SSE 连接关闭回收 — ✅ 通过（修正预期）

方法：容器内直连 `127.0.0.1:8054`（**避开 docker-proxy**），建组 → 建 SSE → 分别以 FIN / RST 关闭 → 轮询 `GET /stream/subscriptions/<sid>` 的 `conns`：

```
FIN close: alive_conns=1  reclaimed_after=19.06s
RST close: alive_conns=1  reclaimed_after=19.05s
```
- 回收延迟 ≈ `STREAM_PING_INTERVAL`(20s)，即**在下一个 ping 写失败时回收**，符合设计；P1-3 要消除的「stream 结束后 `handle()` 重入 `handle_one_request` 再钉 40s」**未再出现**（19s < 40s）。
- 管理请求延迟全程 ~0.001s，worker 未枯竭（池 = MAX_STREAM_CONNS(100) + `_MGMT_WORKER_RESERVE`(10)）。
- ⚠️ **观测陷阱**：从**宿主机**经 docker 端口代理访问时，同一测试 `conns` 持续 1 达 **70s+**（userland proxy 未随 curl 退出关闭容器侧 socket）。这是环境假象，**非缺陷**；后续同类验证须容器内直连。
- `stream_slow_client_total=4` 的观测值 = 验证过程中 4 次主动粗暴断连的计数，属 BR-STR-35 正常行为，非缺陷。

## 6. 缺陷清单

### BUG-P8-01 — P0：`_rekey_batch_response` 回写方向颠倒，点号形式 `/stock/data` 返回垃圾 body

- **位置**：`china_finance_rss/server.py:688`，函数 `_rekey_batch_response`（跨批衔接新增，HEAD 无此函数）。
- **代码**：
  ```python
  else:
      out[key] = rename.get(key, key)     # ★ 把「新键」写成了「值」
  ```
  正确应为重键（保值）：`out[rename.get(key, key)] = value`。
- **机理**：跨批衔接让 `_handle_stock_batch`（server.py:1132）以 canonical 码调 handler，故 `build_batch_response` 把 body 键成 canonical；`_rekey_batch_response`（:1150）负责折叠回客户端拼写。同函数 `_errors` 分支（:684）只改键、正确；主分支却写成 `out[canonical] = requested`，把值覆盖成了拼写串。
- **影响面**：
  - 仅当请求含**被重拼写的写法**（`600519.SH` / `000001.SZ` / 混写）触发；纯 `sh600519` 形式走 `any(...)` 早返回，不受影响。
  - 症状：HTTP **200** + body `{"sh600519": "600519.SH"}`，**无错误信号**（静默数据错误）。
  - 连带 `/stock/fundflow`、`/stock/timeline` 同路径（同一 `_handle_stock_batch` 调用点）。
- **回归性质**：HEAD 版本 `_handle_stock_batch` 直接把原始 `stock_codes` 传给 handler，点号形式返回的是按 `600519.SH` 键好的正常数据 → **可用**。本批新增 canonical 折叠 + 回写后**退化**。属跨批接口（`config.canonical_code` 接入 server.py）引入的回归。
- **证据**：4 条单测失败（§2）+ 生产 HTTP 实测 `{"sh600519": "600519.SH"}`（§5.2）。
- **处置建议（未执行，遵只读约束）**：改 :688 为 `out[rename.get(key, key)] = value`；随后重跑 `tests.test_server_http`（应 4 失败转全绿）+ 回归 `600519.SH` 生产请求。

> 附带（P2，非阻断）：`_rekey_batch_response` 会被应用在 `_guard` 已经按 requested 键好的降级体上（server.py:1147→1150 双重变换）。修好 :688 后该路径退化为幂等 no-op，可接受；但更清晰的做法是 `_guard` 降级体不再二次回写。

## 7. 结论
