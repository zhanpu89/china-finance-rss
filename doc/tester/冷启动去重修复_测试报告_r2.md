## 4. 3B：quote 50 码稳态节拍 — ⚠️ 8s（非 4s），根因非 loop

**方法**：容器已热后 `dedup_probe.py --mode quote --dur 40`（另用 `cadence_probe.py` 0.25s 粒度采样交叉验证）。

| 运行 | 相邻帧间隔(s) | min | <2s |
|---|---|---|---|
| dedup_quote(40s) | 8.009, 7.998, 8.000, 8.048, 8.049 | 7.998 | 无 ✅ |
| cadence(20s) | 8.03, 7.98 | 7.98 | 无 ✅ |
| newcomer A 段 | … 8.01 … | 8.01 | 无 ✅ |

**无 <2s 间隔 ✅，但节拍 ≈8.0s，不是任务预期的 ≈4s — ❌ 偏离验收。**

**根因（用 `cadence_probe.py` 定理级定位，非 loop 变慢）**：同一 quote 组内同时采样

```
push loop 轮次（stream_tick_duration_ms 变化）: 0.53, 4.13, 8.50, 12.07, 16.48   ← 每 ~4s 一拍
真实发送    （last_push_ts 变化）           : 0.53,        8.50,       16.48   ← 每 ~8s 一次
SSE 到达帧                                  : 0.32,        8.35,       16.33
```

- **push loop 仍严格 4s 一拍**（4.13、12.07 两轮照常跑），故非吞吐/网格回归；`degraded=slip=0`。
- 4.13、12.07 两轮**产出的内容与上一拍逐字节相同**（缓存命中），被发送层去重跳过 ⇒ 客户端可见节拍 4s→8s。
- 这与 `quote` 的 **TTL(L0=4s) == tick(4s)** 别名有关：偶数拍命中缓存、奇数拍才真正换数据。r1 §3 已记录**修复前**的同一现象——相邻帧字节成对相同（`58264/58264`、`58274/58274`）。**本次去重正是把这一半重复帧去掉**。

**性质判定**：这是**预期内的去重并合**，不是数据新鲜度退化——修复前 4s 帧里有一半是重复、真实新数据同样约 8s 一次；修复后每隔 8s 一帧、但**每帧都是新内容**（churn 49–50/50）。唯一变化是**客户端可见的推送节拍减半**。

**待决策（tester 不改码）**：任务步 4 明确要求"quote 50 码稳态节拍 ≈4s"，实测 8s。若该 4s 节拍属对外承诺，需二选一：① 调整 `quote` TTL 与 tick 解耦（如 TTL=tick/2）使每拍都有新数据；② 接受 8s 节拍并订正验收口径（数据新鲜度未变）。若 4s 只是"去重前"的观测值，则本项为**口径订正**而非回归。

## 8. 结论

1. **P2（BUG-冷启动-01）核心目标闭环 ✅**：上轮 3 域冷启动首间隔 0.535–0.623s 的重复帧已被发送层去重消除，本次**最短间隔 2.499s、无任何 <2s 间隔**；`FrameDedupTests` 4 例全绿；运行时 `consecutive_identical_content=0` 佐证保证 ④。
2. **内容更新不受损 ✅**：3 域 13 帧 13 个互异签名、每转换 15–50/50 码变化；3C 新连接仍在 3.104s 内收到（未变内容）**强制补发**帧。
3. **无 P0/P1 阻断项。1 项 P2 观察**：`quote 50` 客户端可见节拍 **4s→8s**。根因是去重把 TTL==tick 别名下"偶数拍缓存命中的重复帧"并合掉，**push loop 仍 4s 一拍**、`lag=0`、数据新鲜度未退化。任务步 4 的"节拍≈4s"口径与之冲突，**待编排层决策**：调整 TTL/tick 解耦，或订正验收口径。
4. **次生观察（低优先，建议顺手修）**：`push_loop` docstring 中 `*interruptible* —` 之后多出 5 个空格（diff 引入的排版噪声），无功能影响。
5. **未覆盖**：非盘中 L1=120s 唤醒行为；高并发（≥8 组满配）去重下的连接级 `sent_any` 状态一致性；跨进程/长连接（>5min）去重状态 `last_sig` 的内存恒定性仅由代码与单测保证。
