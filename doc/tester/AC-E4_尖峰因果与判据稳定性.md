## 2. 任务 1：60s 尾尖峰 ↔ `_CACHE_SWEEP_INTERVAL` 的因果判定

### 2.1 已核实的代码事实（决定实验必须怎么做）

| # | 事实 | 位置 |
|---|---|---|
| F1 | `_CACHE_SWEEP_INTERVAL = 60.0`（模块级常量） | `cache.py:39` |
| F2 | `_cache_put()` **在持 `_cache_lock` 期间**，若 `now - _last_cache_sweep >= _CACHE_SWEEP_INTERVAL` 就调用 `_sweep_expired(d)`，随后更新 `_last_cache_sweep` | `cache.py:165-170` |
| F3 | **读热路径也取同一把锁**：`fetch_json` 段①（缓存命中）进入 `with _cache_lock` 查 `cache.get(url)` | `cache.py:796-805` |
| F4 | 清扫是纯 O(n) 扫描 + 删除：`[k for k,entry in d.items() if …]` 然后逐个 `del` | `cache.py:114-133` |
| F5 | `feed_cache_put` 用**同一个** `_CACHE_SWEEP_INTERVAL` 常量清扫 `feed_cache`（上限 100，AC 负载只触达 5 个 feed key） | `cache.py:1036-1038` |
| F6 | **触发条件是"间隔后的第一次写"**，不是独立定时器 —— 若期间没有 `_cache_put`（无 miss），清扫不会触发 | `cache.py:168` |
| F7 | 全仓仅此一处 60s 常量参与缓存清扫（另见 §4 的其它 60s 候选，均非本常量） | `grep` 结果 |

**推论**：要证伪/证实因果，必须做到两件事：(a) 让清扫**按可调周期真实触发**（需要持续的缓存写）；(b) 观测**同一把锁的读热路径**尾延迟。因此实验必须在**进程内**把服务跑起来并 monkeypatch 常量 —— 对已部署容器无从注入常量。

### 2.2 实验设计（三组对照）

新增 tests-only harness `tests/ac_e4_sweep_causality.py`（复用 `tests/test_server_http.py` 的"进程内起真实 HTTP 服务"模式：`BoundedThreadPoolServer(('127.0.0.1',0), RSSHandler, max_workers=20)`）。

**如何让清扫真实触发且可观测**：把 `/finance/market`（panel 路由，`_PANEL_HANDLERS` 按 `server.py:1219-1222` 分发）的 handler 换成**只做 `cache.fetch_json(url, ttl)` 的合成驱动**，并用 `mock.patch.object(cache_mod, 'urlopen', …)` 把上游替换为**零延迟合成响应**（`tests/test_server.py` 的 `_FakeResponse` 模式）。于是：

- 请求 → 真实 HTTP → 真实 `RSSHandler` → 真实 `fetch_json`（段①锁 / 段③写）→ 真实 `_cache_put` → 真实 `_sweep_expired`；
- `ttl=1s` ⇒ 缓存持续失效 ⇒ **写持续发生** ⇒ 清扫按 `_CACHE_SWEEP_INTERVAL` **精确触发**（F6 被消除为混淆）；
- 记录：每次 `_sweep_expired` 的**调用时刻 + 临界区耗时 + 删除条数**（包裹 `cache_mod._sweep_expired`，因它在 `with _cache_lock` 内被调用，其耗时**就是**延长持锁的时间）、请求逐条延迟、`len(cache)` 时序。

**三组对照**：

| 组 | 目的 |
|---|---|
| **A 周期跟随（决定性）** | `interval=60` vs `interval=10`（明显异于 60）同负载同结构；若尖峰周期随常量移动 ⇒ 因果成立 |
| **B 最坏规模** | `cache-size=1500` 预置常驻条目（`MAX_CACHE_SIZE=2000` 的近满载），使清扫扫描量为生产（~50 条）的 30 倍 |
| **C 阳性对照（方法灵敏度）** | 在清扫内**注入固定耗时**（20ms / 100ms）并令 `interval=5`。若这都测不到 5s 周期尖峰，则"无尖峰"才是可信的**阴性**结论 |
| **D 关闭对照** | `interval=1e9`（等效关清扫），验证负载本身不产生周期尖峰 |

另外做**独立佐证**：直接对满载字典计时 `_sweep_expired`，量级与生产观测尖峰幅度比对。

### 2.5 阳性对照：证明"阴性结论"不是方法失灵

同一 harness，`interval=5`，**在清扫内注入固定持锁耗时**（注入点位于 `_cache_lock` 内，故等价于延长临界区）：

| 阳性对照 | 注入持锁 | 清扫间隔 | 桶 P99 中位数 | 桶 P99 区间 | 桶 max 区间 | 每桶 >20ms 请求数 |
|---|---|---|---|---|---|---|
| PC-20ms | 20 ms | 5.05 / 5.01 / 5.02 / 5.03 s | 2.55 | 2.462–2.625 | 22.31–23.91 | —（P99 未动） |
| **PC-100ms** | **100 ms** | 5.02 / 5.01 / 5.00 / 5.01 s | **33.48** | **33.16–38.51** | 101.96–105.04 | **8（= 并发数）** |

**结论**：本 harness **确有能力**检出"清扫持锁 → 尾延迟尖峰"，且检出的是**与常量同周期的尖峰**（100ms 注入 → 5s 周期的 P99 33–38ms vs 基线 2.3ms）。因此 §2.4 的"无尖峰"是**可信的阴性结论**，不是灵敏度不足。

### 2.6 为什么单次清扫**无论如何**都搬不动 P99（放大上界推算）

一次锁获取只能阻塞**在飞**的请求，其上界是 `min(客户端并发 c, 服务端 worker 数)`；锁一释放，排队的请求在微秒级全部放行。因此：

```
每次清扫受影响请求数 ≤ min(c, 到达率 × 持锁时长)
某桶 P99 被抬升的必要条件：该桶内受影响请求数 > 1% × 该桶请求数
```

用两组阳性对照反推验证该模型：

| 场景 | 持锁 | 到达率 | 受影响/次 | 桶内请求数 | 受影响占比 | 预测 | **实测** |
|---|---|---|---|---|---|---|---|
| PC-20ms | 20ms | 150/s | min(8, 3)=3 | 750 | 0.40% | P99 不动、仅 max | ✅ P99 2.46–2.63，max 22–24 |
| PC-100ms | 100ms | 150/s | min(8, 15)=**8** | 750 | **1.07%** | P99 ≈ 持锁时长 | ✅ P99 33–38，max ~102 |

**代入生产 AC 参数**（interval=60s、rate=200 req/s、c=10、`MAX_WORKERS=20`）：
- 每个清扫周期最多影响 **≤10** 个请求；30s 桶内有 6000 个请求 ⇒ 占比 ≤ **0.167% < 1%**。
- 即使持锁时长 **趋于无穷**，占比也只由 `min(c,…)` 封顶在 0.167% ⇒ **单次清扫在数学上不可能抬升 30s 桶 P99**（5s 桶时才刚好 1.0%，且还需持锁 ≥100ms）。

⇒ 结合 §2.3（真实持锁 0.03ms）、§2.4（各设置下无尖峰）、§2.5（方法确有灵敏度），**"清扫本身耗时"与"清扫期间持锁导致的等待放大"两条假设同时被否证**。

### 2.7 因果结论与替代解释

> **因果结论：不成立（已否证）。**
> 60s 尾尖峰**不是**由 `cache._CACHE_SWEEP_INTERVAL=60.0`（及其 `_sweep_expired` 清扫）引起：
> ① 清扫周期确实跟随常量（60→60.05s / 10→10.01s），但**任何设置下都无延迟尖峰**（含 1500 条近满载与"关闭"对照）；
> ② 清扫临界区耗时（真实规模 p99 = 0.032ms；2000 条理论上限 p99 = 0.424ms）比观测尖峰幅度（+30～40ms）小 100–1000 倍；
> ③ 按锁定放大模型，单次清扫在生产参数下最多影响 0.167% 的请求，**数学上不可能**抬升桶 P99；
> ④ 阳性对照证明本方法能检出同周期尖峰（100ms 注入 ⇒ 5s 周期 P99 33–38ms）。
> **不需要**为 `_CACHE_SWEEP_INTERVAL` 做任何代码侧修复。

**替代解释（含证据强度与未验证项，如实标注）**：

1. **突发不是"周期"而是"不规则簇"（本轮新证据，强）** —— 当前环境 5 次 AC 运行的 **5s 分桶 P99** 在 **lag=12（60s）自相关** = −0.026 / 0.063 / **0.802** / −0.006 / −0.054，lag=6（30s）≈ 0（−0.024…−0.106）。**只有 1/5 次**呈现 60s 成分 ⇒ 上轮"~60s 周期尖峰"很可能是**30s 分桶 + 偶然相位**造成的假象，而非稳定周期。
2. **尾尖峰 = 缓存未命中（回源）请求的延迟（强）** —— 本轮 `cache_hit_ratio = 0.976–0.994`；每 1000 样本的 5s 桶里，P99 对应约 **10 个**请求，与"1% miss"量级一致；尖峰桶的 max 达 100–1600ms（单请求级），且 `connect p99` **恒定 0.50–0.89ms**（§3.4）⇒ 尖峰在**服务端响应段**（上游取数），不在客户端建连。**未验证**：无逐请求的 hit/miss 打点（需改生产代码，超出权限）。
3. **上游/CDN 抖动（中）** —— 负载真实回源至 cls.cn / eastmoney 等；`/cls/hotplate`（3 路 fan-out）与 `/stock/timeline` 为最慢端点（P99 9.1 / 8.1–9.8ms，§3.4），合成 P99 由它们主导。
4. **其它 60s 候选（未验证，代码证据）** —— 若仍需解释"60s"：
   - `cdp_engine.py:784` `_heartbeat_interval()` **非交易时段返回 60**（交易时段 10）；15 个 CDP 页各有心跳线程按 60s 轮询 ⇒ 容器内存在真实的 60s 节拍 CPU/IO 活动；
   - `config.py:53` `HTTP_POOL_IDLE_TTL=60` ⇒ 池内连接空闲 60s 被回收，稀疏 host 的下次取数需重做 TCP/TLS 握手（可解释 100–400ms 单发毛刺）；
   - `stream.py:1045` 分组清扫每 60s（本次 AC 无 SSE 分组，**未激活**）。
   **以上三条均未做对照实验**（需容器内打点/exec，超出本轮只读权限），仅登记为候选。
5. **GC / 分配器毛刺（弱）** —— 各组都出现偶发单发 max 毛刺（9–40ms）且与清扫时刻无关；`--mode timing` 中亦见 37.9ms 单次 max。属背景噪声，非周期性来源。

## 4. 结论与建议

### 4.1 结论

1. **任务 1（决定性）**：**`_sweep_expired` 不是 60s 尾尖峰的来源 —— 因果不成立**。清扫周期**确实**跟随 `_CACHE_SWEEP_INTERVAL`（60→60.053s，10→10.006–10.101s，关闭→0 次），但在**任何**设置下、包括 1500 条近满载与"关闭"对照，都**观测不到延迟尖峰**；清扫临界区 p99 = 0.032ms（真实规模）/ 0.424ms（2000 条理论上限），比尖峰幅度小 100–1000 倍；且按锁定放大模型，单次清扫在生产参数下最多影响 0.167% 的请求，**数学上不可能**抬升桶 P99。阳性对照（100ms 注入 ⇒ 5s 周期 P99 33–38ms）证明方法本身有效。
2. **任务 2（AC 口径，未改动）**：当前环境 **5/5 PASS**，劣化比 0.2533 / 0.8632 / 1.0886 / 0.5070 / 0.4133（限值 1.2）；吞吐 200.0 req/s、错误 0/300000。
3. **诊断口径（非 AC）**：5/5 ≤ 1.0，3/5 聚集在 0.88–0.97，方差明显小于 AC 口径；两口径结论一致。
4. **60s 周期尖峰在本环境未复现**：5s 分桶 lag-12 自相关 ≈ 0（仅 1/5 次 0.802）。上轮"~60s 周期"更可能是 **30s 分桶 + 相位巧合**。
5. **判据仍有结构性弱点**：4/5 次 A > B（早期窗口更慢），A 窗口波动 3.8×。极端组合（A=6.6 / B=8.66）比值 1.31 > 1.2 仍可能偶发 FAIL —— **判据的方差来自 A 窗口的瞬态，不是服务端稳态退化**。

### 4.2 建议

#### (a) 代码侧：**无需**为 `_CACHE_SWEEP_INTERVAL` / `_sweep_expired` 做任何修复

本实验已否证其嫌疑（§2）。**不建议**为其做分片/异步化改写 —— 那会是无证据的改动。

若仍需追查残余不规则尖峰，**下一轮低风险动作**（按性价比排序，均非本轮可做）：
1. 对 `_cache_put` 的**真实持锁时长**做进程内打点（本轮只打了 `_sweep_expired`，未含 `_sweep_expired` 之外的写路径），并同时记录 miss/hit；
2. 验证 §2.7-4 的三个 60s 候选：临时关闭/调大 `HTTP_POOL_IDLE_TTL`、交易时段与非交易时段对比（CDP 心跳 10s vs 60s）、`/proc` 级 CPU 打点与尖峰时刻对齐；
3. 若要排除上游，可用"本地监听端口替换上游 URL"做受控回源实验。

#### (b) AC 口径：**建议澄清窗口定义**（**不改 PRD —— 那是 prd-writer + review-expert 的权限**）

> **只提出建议**，理由与影响面如下。

- **问题**：AC 原文把 **前 2min 当作"基线"**，隐含假设"起始最快、之后退化"。实测相反：4/5 次 **A 窗口更慢**（A P99 6.60–25.15ms vs B 6.32–8.66ms），因为 A 覆盖**冷启动瞬态**（终端缓存/负缓存/首批回源、连接池预热）。于是该判据实际度量的是 **"瞬态有多重"** 而非"稳态是否退化"，且**瞬态越轻越容易被判 FAIL**（上轮 run1 的唯一 FAIL 正是 A 窗口"异常干净"所致）。
- **影响面**：判据入口是 `tests/ac_e4_verify.py` 的双窗口比较；修改窗口定义**只影响 AC-E4 判定**，不影响任何生产代码与其它 AC。跨环境/跨轮对比性会改变（需重新建立基线）。
- **建议候选（三选一或组合，供裁决）**：
  1. **基线窗口后移**：基线 = `[60,180]`，对照 = `[180,300]`（去掉瞬态，等长）；本轮该口径 5/5 ≤ 1.0；
  2. **多次取中位数**：≥3 次重复、取劣化比**中位数** ≤ 1.2（抗单次相位噪声）；
  3. **分位数口径**：用 5s 分桶 P99 的**中位数**（而非全窗口单点 P99）比较，抗单发毛刺。
- **不建议**：降低阈值或改成"错误率 + 吞吐"二判据（会丢掉"稳态不退化"这一有效诉求）。

#### (c) 其它

- `BUG-AC-E4-02`（`upstream_fetch_total` 语义不一致）：**已由 `157aa94` 统一**（margin 现仅在终端缓存 miss 时自增，`market_api.py:99`）；本轮 `upstream_fail_total={}` 亦佐证。建议关闭该 BUG 项（本条**仅建议**，由编排层裁决）。
- 本 AC 下**未观察到**内存/503/负缓存风险；上轮 AR-18 的 ~250MiB headroom 残余在本环境变为 **~950MiB headroom（RSS 34–36%）**。

## 5. 限制与不确定性（如实标注）

1. **进程新鲜度是共变量（最重要的限制）**：本轮 AC 的 5 次运行在 **15:50:08 重建**的容器上进行（up ≈40min，RSS 34–36%），而上轮 FAIL 时容器为长跑进程（RSS 81–84%）。因此 §3.7 的改善**不能单独归因**于 margin 终端缓存；要归因需做**同进程长跑 vs 重建后**的 A/B（本轮未做）。
   另需纠正任务书的一处前提：`HTTP_POOL_MAX_PER_HOST=48` / `MALLOC_ARENA_MAX=2` **在上一轮报告时已在 compose 文件中**（上轮 §0 即引用之，见 §1 时间线），故它们不是本轮新增变量；且旧容器**是否实际应用**这两项现已不可回溯（无 `docker inspect` 权限）。
2. **任务 1 的 harness 使用合成上游与合成 handler**：`cache.urlopen` 被替换为**零延迟**合成响应，`/finance/market` 被替换为只调用 `cache.fetch_json` 的驱动。因此它**忠实复现了锁/清扫/写路径**，但**结构上不可能复现"上游网络抖动"**这一替代解释。这是刻意的隔离设计（要证否清扫，必须先排除上游噪声），但也意味着它**不能**用来证否 §2.7-2/3。
3. **任务 1 未打点 `_cache_put` 的完整持锁时长**：只包裹了 `_sweep_expired`（其耗时即清扫额外贡献的持锁时间）。`_cache_put` 的其余部分（插入、`move_to_end`、gauge 发布在锁外）为 O(1)，且 §2.6 的上界论证不依赖该打点。
4. **阳性对照的"注入持锁"是人为的**：用于验证方法灵敏度，不代表生产存在这样的持锁；其数值（20ms / 100ms）是为覆盖量级而选，非实测。
5. **`>=100 req/s` 的负载实现取 200 req/s**：与上轮一致（判据下限的 2×，更严）。AC 原文为 "≥100 req/s"，故 200 属**保守超集**；若按 120 req/s 跑，A 窗口瞬态更轻，判据行为可能不同（上轮 120 req/s 单次比为 1.000）。
6. **尖峰相位与统计功效**：5 次运行的尖峰簇相位各不相同，无法用"全局墙钟周期"解释，也无法排除"上游随机抖动"；`lag-12` 自相关样本仅 60 桶、12 个重叠点，统计功效低（r3 的 0.802 不宜外推）。
7. **未覆盖**：交易时段（TTL 分层不同、CDP 心跳 10s）、SSE 并发负载、长跑 ≥1h 的稳态；`/stock/f10` 与 4 个 CDP panel 按上轮约定**排除在负载池外**。
8. **容器内不可观测**：受只读权限约束，无法 `exec` 进容器做 CPU/GC 打点，故 §2.7-4 的三个候选**未验证**。
