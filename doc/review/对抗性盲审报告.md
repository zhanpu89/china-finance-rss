# 对抗性盲审报告（P8 / `>>MODE: blind`）

- **审查范围（入参）**：需求原文「短线交易系统：处理与响应须高效、准确、稳定」+ 6 模块
  `config.py` / `cache.py` / `metrics.py` / `stock_api.py` / `market_api.py` / `cdp_engine.py`
  （含同目录 `tests/` 作为有效性核对）
- **零上下文纪律**：未读 `doc/review/**`、`doc/tester/**`，未接触任何设计理由、前序评审或测试结论；
  结论仅由需求原文 + 代码本身推出。
- **审查方式**：B2 对抗性假设（输入可恶意 / 依赖最坏时刻失效 / 并发点必被验证 /
  边界值行为未知 / 中间层必漏 / 需求存在未覆盖分支）。

## 评审结论

❌ **阻断**：6 个 P1、7 个 P2。最严重的是**系统把「自己的预算耗尽 / 自己的锁等待」当成上游故障写入
120s 冷却账本**，在负载高峰自我放大为「整备自选股停止刷新」；其次 CDP 导航锁**无超时等待**可占满准入
配额，把 CDP 的慢传染成全站 503。另有一处**心跳缺失页的陈旧数据被无限期当作新鲜数据再签发**。

## 问题清单（按最坏后果排序）

### P1（阻断级，建议修复）

**1. 【P1】`stock_api.py:337-346,349-362,447-453` + `cache.py:318-322`：本地预算耗尽被当成上游故障写入共享冷却账本。**
依据：`_fetch_one`/`_run_batch` 在 **deadline 已过**时直接产出 `'upstream_timeout'`（`stock_api.py:339-340`、`358-362`），
`_process_chunk` 第⑥步对**任何** kind 调 `_fail_ledger_record_failure`（`447-453`），3 次即 120s 冷却
（`FAIL_THRESHOLD=3`/`FAIL_COOLDOWN=120`）。而 `cache.py:318-322` 对同类情形明确「local wait budget, not an
upstream failure ⇒ never record」。测试 `tests/test_data_layer.py:162-177` 把该行为固化为断言（绿但同时锁定缺陷）。
影响：一次大池/慢批（stream 可把整个去重池交给 `_handle_cached_batch`，`_MAX_BATCH_SIZE=50` 分片）过 15s 后，
**尾部全部 code 会被记一次失败**；连续 3 次即把大批自选股打入 120s 冷却 → 客户端 `null`+`_errors`、
stream 帧静默停更。冷却是**自造**的，与上游健康无关 → 自我放大。
建议：区分「本地预算/等待」与「上游失败」——`_process_chunk` 只对网络类 kind 记账（或在 kind 上增加
`local` 标记），本地超时改为返回 `upstream_timeout` 但**不写账本**，与 cache 层 S1-1 规则对齐。

**2. 【P1】`cdp_engine.py:1270`（并 `1272-1301`、`1302-1341`）：导航锁无超时 `acquire()`，无限等待把 CDP 慢传染成全站 503。**
依据：`navigate_stock` 先 `self._navigate_lock.acquire()`（无 timeout），**入参 `timeout` 只在拿到锁后**才被检查
（`1272-1274`）；持锁期间可跑 `min(15, remaining)` 的 load 等待 + `max(2, remaining)` 的轮询（≈60s）。
调用链 `fetch_cls_f10 → _navigate_f10(stock_api.py:569-584) → navigate_stock`，`_handle_cached_batch` 传入的
60s chunk deadline 对**排队等待**完全不生效。仅 3 个导航页（`config.stock_nav_page_names()`）承载所有并发
`/stock/f10`，而准入 `MAX_INFLIGHT=40`（`config.py:25`）。
影响：并发 f10 时等待线程无界堆积并占用准入槽位 → 新请求（含 `/healthz`）被 503（`http_503_total`），
即「CDP 慢 → 全站不可用」，直接违背「稳定/延迟上界」。
建议：`acquire(timeout=remaining)`，超时即按 A' 形态降级；或把排队等待计入请求 deadline。

**3. 【P1】`cdp_engine.py:1093-1099,1142-1144,1264-1267` + `server.py:1262`：心跳缺失页的陈旧数据被无限期当作「新鲜」再签发。**
依据：`_reconnect` 清空 `_key_last_seen` 却保留 `_last_data`（仅弹 `__ws__`，`1093-1099`）；
`get_data` 对**时钟缺失**的键判定为新鲜（`last_seen is None or ...`，`1142-1144`）；
`_last_data` 的老化只发生在 `_ingest_payload`（`843-849`），而导航页以 `heartbeat=False` 创建
（`server.py:1262`）→ 唯一会触发老化/刷新时钟的路径正是 `navigate_stock` 的快路径所跳过的导航
（`1264-1267` 只比对 `secu_code`，**无任何 age/TTL 校验**）。
影响：一次 reconnect（心跳失败、每 30 次导航的 `_maybe_reconnect`、每 2h Chrome 重启）后，页面对同一
code 永不再导航，`get_data` 持续返回重启前快照；`fetch_cls_f10` 再把它作为成功结果经 `_cache_store`
（`stock_api.py:458`）**以新 ts 写入 300s 终态缓存** → 陈旧数据被反复盖章为新鲜，短线场景的「准确」失守。
建议：快路径加入 `_last_data_max_age` 校验；`_reconnect` 同时清理 `_last_data`/`_last_data_ts`，
或让 `get_data` 以 `_last_data_ts`（而非被清空的 `_key_last_seen`）做老化判断。

**4. 【P1】`stock_api.py:171-175`（并 `196-210`）：失败账本满额后**每次**失败写都做 O(n log n) 排序且持锁。**
依据：`_fail_ledger_prune_locked` 只在 `len > _FAIL_LEDGER_MAX(=10000)` 时 `sorted(...)` 全表；
持续故障下 `e[3]`（最后写入时刻）被不断刷新，限速的老化扫描（`165-170`）**删不掉任何条目**，于是每次写入
都回到 10001 条 → 每次都排序 10001 键；该排序与 `snapshot` 构建均在 `_fail_ledger_lock` 内（`206-209`）。
而 `opened` 转 true 时**绕过** `_COOLDOWN_PUBLISH_INTERVAL`（`207`），冷启动+上游不可用时会连续触发 O(n) 快照。
影响：正是 S1-3 声称修掉的「n 次失败 O(n²)、且串行在账本锁上」的降级路径**仍存在**；账本锁同时被每批
每个 code 的 `_fail_ledger_get`（`435`、`1036`）争用 → 上游挂掉时 API 反而更慢。
测试盲区：全库无 ≥10000 条的用例（`tests` 最大 2000 条），该分支从未被执行。
建议：硬上限改为 O(1) 淘汰（如按插入序/环形结构或分批摊销），把 `opened` 转 true 也纳入发布限速。

**5. 【P1】`cache.py:237-240` 与 `stock_api.py:255-256`：deadline 闸门置于正缓存之前，过期预算会拒绝「已在缓存里的新鲜数据」。**
依据：`fetch_json` 文档声明的四段协议第①段是「正缓存命中即返回」，但代码把 `deadline` 闸门放在
`segment 1` **之前**（`237-240` 先于 `242-250`）；`_fetch_rest_json` 又在 `255-256` 先做同样的闸门。
`handle_cls_stock_batch` 以 `pool=None, cache=None` 调用（`985-996`），即 `/stock/data`（`server.py:467`）
**只有 URL 缓存**，而在闸门之后根本读不到它。server 侧 `handler(stock_codes, dropped=...)`（`server.py:997`）
也未传 deadline，budget 由 handler 内造 15s。
影响：慢批一过 15s，剩余 code 即使 URL 缓存命中且在 TTL 内也一律 `null` + `_errors.upstream_timeout`
（本地超时），并被第 3 条记账放大 → 负载越高，「缓存越救不了」。
测试盲区：`test_elapsed_deadline_raises_without_network` 用的 URL **不在缓存**，恰好绕开该组合。
建议：把 deadline 闸门移到正缓存命中之后（缓存命中零网络、零延迟，本就不该被预算拒绝）。

**6. 【P1】`config.py:74` + `stream.py:159-171` + `server.py:985` + `stock_api.py:587-593` + `cdp_engine.py:1309,1332,1345`：股票代码无单一权威规范化，CDP 路径只容忍一种写法。**
依据：`VALID_STOCK_CODE` 同时接受 `sh600519` 与 `600519.SH`（`config.py:74`）；`stream` 入口只做
`strip().lower()`（`stream.py:170`），**HTTP 入口 `_handle_stock_batch` 连小写都不做**（`server.py:985`）。
CDP 侧 `navigate_stock` 用 `bi.get('secu_code') == stock_code`（**大小写敏感、精确相等**：`1309/1345`），
`_company_info_matches` 用 `SecuCode.upper()`（`587-593`）——上游每只股票只有一个固定字符串，因此
「两种被接受的写法」中**必有一种永远不可能匹配**（不确定性：具体是哪种取决于上游 `SecuCode` 的实际返回格式）。
影响：坏写法要么每次烧掉最多 `8s × 3 页` 导航后 `cdp_unavailable`，要么被 `fetch_cls_f10` 判为
**「有数据但不匹配 → 返回 None」**（`883`），而 `None` 按语义是「无数据、不计数、不冷却」（`465-466`）→
**静默 null、无 `_errors`、每个 tick 重新付整次导航**；同一股票还可产生 `SH600519/sh600519/600519.SH/600519.sh`
多个池/缓存键，重复上游调用并稀释 2000 上限的缓存。
建议：在**单一入口**（config 层提供 canonical_code()）把两种写法归一到上游唯一形式，HTTP/stream 共用；
`fetch_cls_f10` 的「不匹配」要按 `cdp_unavailable` 计数而非静默 None。

### P2（记录级，不阻断）

**7. 【P2】`market_api.py:111`：`zb` 绕过 `to_100m`，缺失哨兵 `'--'`/字符串直接进入数值字段。**
依据：`to_100m` 显式处理 `'--'`/`None`（`96-99`），同结构的 `zb` 却写作 `item.get('zb', 0)` 原样返回。
影响：上游缺值时返回字符串 `'--'`（成功体）而 `_degraded` 返回 int `0`（`26-27`）→ 契约类型不稳定，
前端算数出现 NaN/异常。建议：`zb` 也走 `to_100m` 或统一为 `float`。

**8. 【P2】`market_api.py:83-118` + `61-80` + `121-130`：单字段脏值使整份 margin 退化为全 0。**
依据：`float(val)` 的 `ValueError` 发生在 `_transform_margin`，而 `fetch_margin` 的 try 只包住
`json/fetch_json`（`66-73`）→ 异常逃逸到 `handle_margin` 的 `except Exception`（`127-130`），
整份响应变 `_degraded('upstream_error')` 并多计一次失败。
影响：一行脏数据抹掉全部有效行。建议：逐字段容错（`try: float(...) except: 0.0`）或在 transform 内兜底。

**9. 【P2】`config.py:177-189`：`cache_max` 对 URL 缓存类域（plate/news_url/longhu/margin）是死配置。**
依据：唯一消费点是终态存储 `_cache_store`（`stock_api.py:272-283`）、`feed_cache_put`（`cache.py:355`）、
sector 两处；URL 缓存用全局 `MAX_CACHE_SIZE=2000`（`cache.py:29,109-112`），不读 policy。
影响：把 `plate.cache_max` 调小到 50 完全无效，与「endpoint cache max 单一权威」的声明不符，
运维会误判容量。建议：要么删掉这些域的该列，要么让 URL 缓存按域策略取值。

**10. 【P2】`cache.py:273-301`：leader 令牌可在 `try` 之前异常时永久泄漏。**
依据：`_effective_timeout`（→`_fetch_budget`→`_neg_lock`）位于 `try/finally` **之前**，
`_fetch_inflight.pop` 只在 finally 内（`298-301`）。
影响：一旦该段抛异常，该 URL 的选举令牌永不清除 → 之后所有请求都成为 follower，等满预算后按
`leader_alive` 报 `upstream_timeout`（`318-322`）→ 单 URL 永久不可用。概率低但后果为永久性。
建议：把选举+取预算整体纳入 `try/finally`。

**11. 【P2】`cache.py:248,250,261-264,307-312`：`cache_hit_ratio` 系统性低估。**
依据：每次查找先记 miss（`250`），而**双重检查命中**（`261-264`）与**follower 命中**（`307-312`）
均直接 return、不记 hit；hit 路径还在锁内返回、不进 `_cache_put`（唯一的发布点，`118-124`）。
影响：并发/慢上游（正是要观测的场景）下命中率被低估，稳态全命中时 gauge 甚至不再刷新 → 监控失真。
建议：在两条命中路径同样 `_cache_stats['hit'] += 1` 并在返回前发布（或改为独立计数器）。

**12. 【P2】`metrics.py:137-142`：`snapshot()` 只对 dict 值做锁内浅拷贝，list 值在锁外直接迭代实时对象。**
依据：`items` 构建时 `v.copy() if isinstance(v, dict) else v`（`138-141`），list 直接引用原对象，
`_clone` 在锁外执行（`142`）。
影响：一旦有人把 list 型 gauge 原地增删（现均为整体替换，故为**潜在**缺陷），`/healthz` 会
`list changed size during iteration` 或读到撕裂值，违背「绝不阻塞/绝不出错」的自我声明。
建议：锁内对所有可变容器做 `list(v)` 浅拷贝。

**13. 【P2】`metrics.py:92-107` vs `64-89`：`set_gauge` 缺少 `incr` 那样的形状守卫。**
依据：`incr` 对 labeled/unlabeled 不匹配会 warn+忽略（`77-79`、`87-89`），`set_gauge` 的 `key=None`
分支直接 `_gauges[name] = value`（`100-101`），可把 dict 型 gauge（`cache_entries`）整体替换为标量。
影响：一次误用即静默丢失全部标签维度，且无告警。建议：补与 `incr` 对称的守卫。

## 最担心 Top1

**P1-1：把自身预算耗尽写进 120s 冷却账本。** 它不是「上游坏了怎么办」，而是**系统自己把一次慢批
变成对整份自选股的 120s 数据停更**——触发条件是负载本身，而负载又会让更多请求超预算，形成正反馈。
对短线交易而言，这比任何单点慢都危险：客户端看到的是「有 `_errors` 的 null」和停更的推送帧，
而真正的上游可能完全健康。修复优先级高于其余全部条目。
