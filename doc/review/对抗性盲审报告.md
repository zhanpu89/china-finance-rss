## 发现问题（按严重度；均 ≤P2，无 P0/P1）

### 【P2】cdp_engine.py:458 — 硬上限 evict **成功**路径漏 pop `_close_failures`，死条目永久滞留

**证据链**：`evicted` 被 force-evict 的前提是它处于 throttle 窗口内（L445-448 软 evict 扫描全部跳过 → L449-455 硬上限兜底），即**必然已存在 `_close_failures[evicted]` 条目**。此时若 `_close_one_target(evicted)` 返回 **True**（close 成功，或 Chrome 已死返回 "No target with given id"），L458 `if evicted and not ...` 整支不执行——成功分支被静默跳过：
- `_created_targets` 中该 id 已被 pop（L454）→ 永久离开台账
- 但 `_close_failures[evicted] = (ts, count)` **无人删除**（pop 只在 L463 失败分支 / L809 close 成功 / L824 drop 三处，此处均不命中）

**影响（资源正确回收）**：LRU 首个成功回收的硬上限 evict 即留下一个死条目。CDPPage 实例跨 `full_chrome_restart` 存活（L911-964 仅重连不重建对象），故死条目跨 Chrome 重启累积。条目为惰性内存（读侧 L446/L794 只查台账内 id，死 id 永不再入候选），无功能影响，仅内存泄漏 + 日志审计噪音。频率受硬上限路径罕见度约束。

**修复方向**：L458 改为三支处理——`if evicted and not close: <现逻辑>` / `elif evicted: self._close_failures.pop(evicted, None)`。

### 【P2】cdp_engine.py:350,456 — "40" 为每页上限，全局 tab 无界；OOM 正反馈从「台账」转移为「真实 tab」，未被本轮切断

**证据链**：L350 `_HARD_CAP = _MAX_TRACKED_TARGETS + 8` 是实例常量；L368 实例级台账。`init_cdp`（server.py L884-888）默认建 5 页（finance/quotation + 3 stock nav）→ 全局上限 5×40=200 tracked。且硬上限 drop 路径（L460-465）每次把 1 个**已确认存在且 close 失败**的 tab 移出跟踪但**留在 Chrome**——即「放弃追踪 = tab 残留在 Chrome」。每页在"WS 半死但 HTTP 存活"的暴风窗口内，每次 connect 循环（_reconnect 3 attempt × _create_target 均成功创建 tab）可贡献 1 个不可追踪 tab，随 connect 节奏线性累积，**无全局封顶**。

**收敛兜底**：Chrome 2h watchdog 重启（server.py L900-917）+ 暴风期 ensure_chrome 自杀重启（L206 按端口 kill 全量 Chrome）——真正把真实 tab 清零的是重启机制，不是本轮修复。**若有人调大/禁用 `CDP_RESTART_INTERVAL`，本项升级为 P1**（2C2G 上 200+ renderer → 内核 OOM kill Chrome → 全 CDP 端点中断）。

**影响（资源正确回收 / 接口稳定）**：台账收敛目标达成，但 Chrome 内存压力本身未被本轮真正切断。语义被"40"这个名字误导（读者会以为是全局预算）。

### 【P2】cdp_engine.py:793-794,814,824,843 vs 463,470 — `_close_failures` 读写脱离 `_ws_lock`/`_reconnect_lock`，故障窗口内 fail_count 语义失真

**证据链**：
- 写路径：L470 `_close_failures[evicted] = (now, 1)`（`_connect` 内，锁外）、L843 `= (now, fail_count)`、L824 pop（均锁外）
- 读路径：L793-794 候选过滤（`_ws_lock` 块**外**）、L446 evict 扫描（锁内，与 L470 写不在同一临界区）、L814 fail_count 读（锁外）
- `close()`（L1235-1244）不持有 `_reconnect_lock`，可与会话期 heartbeat 的 `_reconnect` 并发执行 `_close_target` → 双线程同时从 `(ts, 2)` 读到 fail_count=2 各 +1 → 均写入 3 → **同一次失败被双计**（提前 drop，tab 永久残留 Chrome）；或丢更新（永不达 3，tab 滞留）
- 附带语义漏洞：L470 强制 `= (now, 1)` **覆盖已有计数**——若 evicted 已 2 连败，force-evict+1 败后计数被重置为 1，"3 连败放弃"承诺被静默延长（硬上限 drop 最终覆盖它，故非功能性错误，但与注释「≥3-failure drop path」语义不完全一致）

**影响（线程安全）**：GIL 保证 dict 读写在字节码级原子，无崩溃/无半写；后果限于计数失真 → drop 时机偏差（提前 1 次或推迟）。故障窗口=Chrome 半死暴风期，恰是计数最该准确的时候。P2（线程安全为系统优先级 #3，但实际影响被 GIL 和重启兜底限制）。

### 【P2】cdp_engine.py:413 — WS 半死暴风下 `_create_target` recv 超时静默泄漏 tab（既有问题，与本轮修复目标交互）

**证据链**：L409-413 `ws.send(Target.createTarget)` → `json.loads(ws.recv())`，`settimeout(5)`。Chrome HTTP 存活但 browser WS 通道堵塞时：createTarget **已成功执行**（tab 真实创建于 Chrome），recv 超时抛异常 → `_connect` 全程无 close 尝试、无台账登记 → **每次 attempt 泄漏 1 个不可追踪且可运行的 tab**。`_reconnect` 每轮 3 attempt + 重启阶段每轮 3 attempt（L937-963）→ 单次暴风循环最多 6 tab/页。数据新鲜优先的系统优先级下，tab 数在 2h watchdog 窗口内可到数百/页。

**判定**：非本轮引入（属既存路径），但本轮「台账收敛 → 防 OOM」的宣称隐式依赖"创建失败必无残留"这一不成立假设。盲审照报。

**修复方向（可留待下轮）**：`_create_target` 改用 `returnByValue` 容错——recv 超时后主动 `Target.closeTarget` 同名 targetId 不可得（id 未返回）；改为在超时时尝试 `ws.recv` 一次延窗口（+2s）或对 `Target.createTarget` 结果用 `Runtime.evaluate` 反查——最低成本方案：超时后重新拉 `/json` 并按 URL/序次识别新增 tab 关闭之。

### 【P2】cdp_engine.py:1244 / 799-802 — close() 的 "5s 预算" 不是硬界，停机最坏 ~40-50s，超容器默认 SIGTERM 宽限

**证据链**：预算只在候选迭代**前**检查（L799），`_close_one_target` 内部无子预算：WS 路径 connect+send+recv 各 ≤2s（L873-875,881）+ HTTP 兜底 ≤2s（L897）≈ 4-5s/个。预算窗口内可执行 **2 个**候选（t0 第 1 个 4s → 第 2 个 4s → 8s 才触发 break）→ 每次 close 调用实际最坏 ~8-10s。`shutdown()`（L1285-1287）5 页串行 → 停机最坏 ~40-50s，超过 Docker/K8s 默认 10-30s SIGTERM 宽限 → SIGKILL 打断清理。

**影响（接口稳定/资源回收）**：无数据损坏（残留 tab 随容器 namespace 消亡；非容器部署则残留至下次 ensure_chrome 复用——注意 server.py L187-191 对**已运行** Chrome 直接复用不 kill，残留 tab 会计入下个生命周期）。代价为重启节奏拉长。与修复目标声明「收敛至 ~40s/5页」一致（声明本身接受此值），故 P2。

## 最可能翻车位置（按风险排序）

1. **L458 evict 成功路径的 `_close_failures` 泄漏**（新代码缺陷，最直接）：修复成本一行，但若被后续维护者当作"evict 成功=已清理"的通用假设，会掩盖其他 pop 缝隙。
2. **每页 40 vs 全局无界 + drop 后真实 tab 残留**（修复目标的语义残留）：台账说谎——账本封顶但 Chrome 内存不封顶；**前置条件：`CDP_RESTART_INTERVAL` 兜底必须保持启用**，否则升级为 P1。
3. **fail_count 锁外读写 + L470 计数覆盖**（线程安全第三条优先级的实际弱点）：故障窗口内 drop 决策偏差，虽被 GIL/重启兜底，但这是唯一能在运行期错误放弃追踪（tab 永久泄漏）的路径。
4. **`_create_target` recv 超时静默泄漏**（既存，风险最高但非本轮）：暴风期内每 attempt 1 tab，是真实 tab 无界增长的最大来源，本轮修复完全未触及。

## 评审结论

**✅ 可合入。**

无 P0/P1；5 项发现全部 ≤P2（4 项为本轮新代码的边界缺陷——其中 L458 泄漏是唯一"本轮引入"的新缺陷，建议随本轮一并修掉；其余为语义/并发/既存残留，记入 P2 待办）。本轮四个修复目标（硬上限锁界、drop→pop、close 5s 预算、预算覆盖完整性）经证伪尝试**全部成立**，核心 OOM 正反馈（台账 +1/暴风轮次）确实被切断。合入前置条件唯一一条：确认生产环境 `CDP_RESTART_INTERVAL`（默认 7200s）未被禁用或放大——该机制是真实 tab 收敛的唯一硬兜底，若被调大/禁用，本报告第 2 项升级为 P1 阻断。
