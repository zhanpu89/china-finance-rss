## 四、问题详情（按 Dim）

### Dim 0 — 契约一致性
跳过（纯后端内部修复，无对外接口/字段变更；HTTP 层截断逻辑 `server.py:636-640` 未动，`/stock/*` 契约不变）。

### Dim 1 — 数据与正确性
- ✅ **P1-1 修复验证（截断回归）：** `_handle_cached_batch`（`stock_api.py:199-205`）`for i in range(0, len(codes), _MAX_BATCH_SIZE)` 分片 + `result.update` 合并 → **全量覆盖**。证据链：stream.py `_refresh_pool`（`stream.py:114`）`handler(list(codes))` 传全量去重池（≤`MAX_DEDUP_CODES=2000`），修复前 `_build_frame` 因 `entry = {}` 永久丢帧（见首轮报告证据链），修复后每个 code 至少走缓存/抓取管道，`_build_frame` 不再因截断丢码。
- ✅ **`_MAX_BATCH_SIZE` 来自 config（=50）**，非魔法数字；分片步长与块上限同源。
- ✅ **cache_ts 守卫（P1-3）交互正确：** 每片独立 `fetch_time = time()`，`existing_ts < fetch_time` 比较语义与原单通道一致（防并发 prefetch 线程回写更旧数据被覆盖）；单片路径（server.py）与旧行为逐字节等价。
- ✅ 空输入 `if not codes: return {}` 提前返回；`if not valid: return result` 保留非法码 None 标记。

### Dim 2 — 并发
- ✅ **P1-02 修复验证（shutdown 竞态）：** `_reconnect:704` 与 `_ensure_ws:784` 循环条件均为 `while self._running and time.time() < deadline`。`close()` 在 L986 先置 `_running=False` → 重试循环下一轮迭代即退出。正常运行时 `_running=True`，条件退化回 `time.time() < deadline` —— **重试语义零变化**。
- ✅ **`_running` 检查位置正确：** 在循环条件上而非循环体内，close() 后最多再跑一轮迭代（ensure_chrome 快速返回 + 3 次 fast-fail 连接 + 2s sleep，有界几秒），45s 白跑消除。
- ✅ **`_close_target` 锁（`cdp_engine.py:650-653`）：** `_ws_lock`（RLock）仅覆盖 tid 原子交换（读 + 置 None），**网络 IO 在锁外**；并发第二次调用读到 `None` 提前返回 → double-close 消除。幂等化不改单次合法关闭行为。
- ✅ **锁序审计：** 全文件唯一跨锁序是 `_reconnect_lock → _ws_lock`（`_reconnect`/`_ensure_ws` 持 `_reconnect_lock` 调 `_close_target` 取 `_ws_lock`）；持 `_ws_lock` 的路径（`_evaluate`/`re_fetch_api`/`_send_navigate`）均不取 `_reconnect_lock` → 无反向序，无死锁。`_ws_lock` 为 RLock，即便 `_connect` 异常路径在持锁时重入也安全。
- ✅ **F10 串行性保留：** `concurrent=False` 沿 `_handle_cached_batch → _process_chunk → _run_batch` 传递，分片外层也是串行 for → 无并发回归（navigate_stock 共享页池不被并行打爆）。

### Dim 3 — 资源与性能
- ✅ **deadline 跨片语义：** 单个绝对 `deadline`（`fetch_cls_f10`/`fetch_cls_basic_infos` 的 `time()+60`）在所有片间共享，`_fetch_one:111` `time() > deadline → None` —— 片与片之间**不透支时间预算**，靠后片的缓存命中仍返回、仅抓取受限。与旧单通道的 deadline 行为完全一致，且比旧的"直接丢弃"多服务了 1950 个码的缓存命中。
- ✅ REST fetcher（fundflow/timeline）忽略 deadline 属既有行为（`_fetch_one` TypeError 降级），非本次引入。
- P2-03 见上（跨片重复码多抓一次，当前调用方不可达）。

### Dim 4 — 安全
无新暴露面。分片仅按 config 常量切 list，无注入/越权相关变更。

### Dim 5 — 结构与可维护性
- ✅ `_process_chunk` 提取干净，原管道逻辑逐行保留（去重→校验→LRU→缓存查→抓取→合并）；docstring 注明"调用方须传 ≤50 列表"，契约清晰。
- ✅ `_handle_cached_batch` docstring 已同步新语义（分片、stream.py 场景），注释与行为一致。

### 逆向审查
- ❓ `close()` 后 `evaluate_fetch`/`navigate_stock` 经 `_ensure_ws` 走 fail-fast → 返回 False/None，调用方（`_evaluate_fetch_any` 返回 None、`navigate_stock` 返回 False）均有降级处理，无空指针。✅
