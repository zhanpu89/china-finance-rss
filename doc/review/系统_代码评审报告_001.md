## 四、问题详情

### 维度 4：性能

**PF-1（P1）Batch handler 逐一串行抓取。**
`handle_cls_fundflow`(145)、`handle_cls_timeline`(251)、`handle_cls_f10`(410)、`handle_cls_basic_infos`(628)、`handle_cls_announcement`(716) 均为：
```
for code in missing:
    data = fetch_cls_xxx(code)   # 阻塞网络 IO
```
`_MAX_BATCH_SIZE=50`，冷缓存且上游慢时单请求可达 50×(单码延迟)；同一请求内的所有 code 无并发。建议对 `missing` 列表用 `ThreadPoolExecutor`（capped）并发抓取再合并入库。

**PF-2（P1）`_evaluate_fetch_any` 串行探测过长。**
stock_api.py:66 遍历 `_STOCK_NAV_PAGES[:3] + ['cls_finance','cls_quotation']`，每个 page 最多 2s，最长 10s+；且每个 page 上的 `evaluate_fetch` 与 TS-2 的导航在同一 WS 上竞争。建议：改为在第 1 个可用页完成即可，降低每页 timeout，并确保与导航互斥。

**P2（可接受项）：** `_cache_put` 满时 `min(d, key=…)` 为 O(200) 可接受；`_sweep_expired` 受 60s 间隔保护；池 LRU 淘汰 `sorted` O(n log n) 上限 500 可接受。

### 维度 5：可维护性

**M-1（P2）大量重复。**
`CDPPage.refresh()`(705-750) 与 `_heartbeat()`(530-624) 的数据合并/过期清理逻辑几乎一致；`fetch_cls_f10`(326) 与 `_f10_direct_fetch`(348) 完全重复；fundflow/timeline/announcement 三个 handler + 三个 direct_fetch 结构同构。建议抽 `_merge_cdp_payload`、`_lru_pool_manager` 共用。

**M-2（P2）`_STOCK_NAV_PAGES` import 时固化。**
stock_api.py:40 `list(stock_nav_page_names())` 在模块加载时执行，运行时改 `CDP_STOCK_PAGES` 不生效。建议改为运行时读取（函数调用或缓存失效）。

**M-3（P2）单码/多码返回不一致。**
server.py:557 单码时 `{code: handler(code)[code]}`，多码返回全量 dict。调用方可感知行为二态，建议统一为多码形态。

### 线程安全（重点维度）

**TS-1（P1）CDP WebSocket 并发写帧无锁。**
`re_fetch_api`(467) 直接 `self._send` 且调用 `_next_id()` 无锁自增 `_msg_id`(366-368)。`_evaluate`(458) 持 `_ws_lock` 读写 WS 期待按 ID 匹配响应。当 heartbeat 线程执行 `re_fetch_api` 的同一时刻，HTTP 请求线程正在 `_evaluate` 内 `_ws_lock` 上等待 -- 两条线程对同一 socket 并发写帧，帧交错后 `_send_recv` 等待的 `id` 永远等不到，导致 response 错配、超时、触发重连。
**修复方案：** `re_fetch_api` 包进 `with self._ws_lock:`；`_next_id()` 用锁保护（在 `_ws_lock` 内递增即可消除竞态）。

**TS-2（P1）`navigate_stock` 裸读 WS。**
cdp_engine.py:855 `self._recv(timeout=2)` 读响应循环未持 `_ws_lock`。stock 页（heartbeat=False）会被 stock_api.py:66 `_evaluate_fetch_any` 并发调用 `evaluate_fetch`（走 `_evaluate`/`_ws_lock`）。两条线程一条在裸 `recv` 消费帧、一条在按 ID 匹配 —— 导航期间的响应帧被 evaluate 线程抢先消费（或反之），导航判定失真、evaluate 超时。
**修复方案：** 读帧循环也归入 `_ws_lock`（或整体合并为单一 `_evaluate` 内完成的导航状态轮询），保证 socket 读写同一时间仅一条线程。

**TS-3（P2）`_nav_restart_counter += 1` 无锁。**
cdp_engine.py:800 类属性整数自增在 GIL 下大多数安全，但非原子；并发下计数可能丢失导致重启频次异常。建议放进 `_chrome_restart_lock`。

**TS-4（P2）feed 锁字典竞态。**
server.py:596/602 在异常或 LRU 淘汰时对 `_feed_fetch_locks.pop(path)`，而另一线程可能已持有该 path 的锁引用正在 `with lock:` 内 —— 后续请求会创建新锁导致同一 path 双路抓取。建议淘汰时仅移除字典条目并容忍短暂双抓，或对锁字典整体加 `_feed_fetch_locks_lock` 保护读写一致性（当前读是持锁的，写（创建）也持锁，pop 也持锁，需确认时序）。

**其他评估为安全的并发点：**
- `get_data()`(689) 返回 `_lock` 保护下的合并副本，`handle_finance_market` 对其 `.pop()` 不影响共享态（正确）。
- `fetch_json` 绊抢：leader/follower 通过 Event 正确；leader 失败时 finally 清 in-flight，follower 转正重试（正确）。
- `_get_or_fetch_feed` 双检锁 + 单 bucket 锁，防击穿正确。
- `_sector_cache/`池 均持独立锁；覆盖读写路径。

### 资源管理

**R-1（P1）sector 缓存写磁盘线程风暴 + 文件损坏风险。**
stock_api.py:537 在 `_populate_sector_from_f10` 内每命中一个 code 就 `threading.Thread(target=_save_sector_cache).start()`。F10 prefetch 一轮可达 300 个 code → 瞬时 300 个线程并发 `json.dump` 到同一 `data/sector_cache.json`：文件被交错写入、可能截断/损坏；线程与磁盘 IO 过载在 2c2g 环境会触发 OOM。
**修复方案：** 单一后台写盘线程 + 队列/去抖（如最后写入后 2s 合并写一次），删除 `_save_sector_cache` 的每次命中 spawn。

**其他资源项（可接受）：** CDP 内存由 3 页 + watchdog 控制（已在前置会话收敛到 ~390MiB）；`cache`/`feed_cache`/各池均有上界（200/100/500/300）；`_last_data` 有 `_LAST_DATA_MAX_KEYS=50`；`--max_old_space_size=512` 限制 V8。

### 维度 3：安全

**S-1（P2）部分接口缺少 stock code 校验。**
`handle_cls_f10`(378)、`handle_cls_basic_infos`(596)、`handle_cls_stock_batch`(768) 均用 `VALID_STOCK_CODE.match` 校验；但 `handle_cls_fundflow`(113)、`handle_cls_timeline`(219)、`handle_cls_announcement`(684) **未校验**，`secu_code` 被无校验拼入上游 URL。虽 target host 固定、非 SSRF，但可注入任意查询字符串探测上游/破坏缓存键。建议三处补 `VALID_STOCK_CODE.match` + 丢弃非法码。

**评估为安全项：** 无 SQL/命令注入面（纯 HTTP 转发）；无越权（无私有数据/鉴权）；签名在服务端计算未泄露；`escape_xml` 覆盖 RSS 输出；`PUBLIC_BASE_URL` 暴露 feed self-link 正常。

### 维度 1：编码规范

- 大量同构代码 → 建议抽公共函数（见 M-1）。
