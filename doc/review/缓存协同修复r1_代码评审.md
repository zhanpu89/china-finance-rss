## 四、问题清单

### P1-1 【新引入·阻塞】stock_api.py:129-130: 入口截断破坏 stream.py 全量池调用

**触发与后果：** 当 {用户创建 >50 codes 的 stream 订阅（合法，上限 `MAX_CODES_PER_SUB=200`；多组去重池可达 `MAX_DEDUP_CODES=2000`）} 时，`stream.py:114 handler(list(codes))` 传入全量池，`_handle_cached_batch` 静默截断到前 50 → 返回 dict 只含 set 迭代顺序前 50 个 key → `_refresh_pool` 中其余 code 的 `result[code]` 保持 `{}` → `_build_frame` 的 `if not entry: continue` 跳过 → **这些股票永久不出现在任何 SSE 帧中**。

**证据链：** stream.py:112-119（result 预填+仅更新返回 key）→ stock_api.py:129-130（截断）→ stream.py:126-128（空 entry 被丢弃）。set 迭代顺序是哈希序，**哪 50 只"有数据"在重启后可能改变**，行为不稳定。

**为什么 P1：** 功能缺陷而非崩溃/数据丢失（不涉及已有持久数据），但属于本次修复**直接引入**的对现有合法功能（>50 订阅）的静默破坏，且无任何告警。`tests/test_stream.py` 的 `_refresh_pool` 测试只用 1 个 code（mock handler），未覆盖此路径——测试盲区。

**修复方向（必选其一）：**
1. 推荐：`_handle_cached_batch` 入口改为**分片循环**——`for i in range(0, len(codes), _MAX_BATCH_SIZE): ...` 每片走原有逻辑并合并 `result`，既保留防御上限又不错数据；
2. 或：将截断上移到 server.py（已存在）+ 移除共享函数内截断，另在 stream 侧显式分片。

### P2-2 【修复不充分】stock_api.py:311-312(及 4 个循环同构): fail_blacklist "跳过一轮即重置"

**触发与后果：** 当 {某个 code 持续失败} 时，计到 3 后 `del` + `continue` **只跳过本轮**，下轮立刻重试 → 坏源实际被打频率为 3/4 passes（fundflow 约 25s 间隔 → 每 ~100s 仍打一次），防雪崩效果有限；且**被 pool LRU 驱逐的 code**（count 1~2）条目永不清理，长期运行小幅内存累积（总量受历史去重 code 数上界约束，P2 级）。

**修复方向：** 若意图是"给坏源降频"，应跳过 N 轮（如跳过 3 轮或指数退避）而非删条目立即重试；驱逐时同步清 blacklist（或将 blacklist 移入 pool 锁生命周期内管理）。

### P2-3 【P1-3 残留】stock_api.py:176-180: 守卫不对称 + 墙钟语义

**触发与后果：** ① 请求线程有 `existing_ts < fetch_time` 守卫，但 4 个 prefetch 循环写缓存**无任何守卫**，无条件覆盖。当前无害（evaluate_fetch/urlopen 在写前完成、`cache_ts=time()` 即写时刻，最新写入者胜），但若未来预取复用 page 快照或慢响应，旧数据可覆盖新请求数据。② `time()` 为墙钟，NTP 回拨时 `existing_ts < fetch_time` 判据可能反转（理论级，单机 RSS 场景概率极低）。

**修复方向：** prefetch 落缓存前也加同款 ts 比较（与请求路径对称）；墙钟回拨问题记录即可，不建议换 monotonic（`_MAX_CACHE_AGE` 是数据年龄语义）。

### P2-4 【P1-7 残留】cache.py:108-127: fall-through 退避+信号量无超时、全局跨 URL

**触发与后果：** 当 {上游持续慢/挂} 时，single-flight 超时后每个 follower 先 `sleep(0~0.5s)` 再 `acquire()`——acquire **无超时**且信号量**全局 2 槽跨 URL 共享**：单请求最坏延迟 = 10s（等 leader）+ 0.5s + 队头持有者 10s（另一 URL 的慢请求占用槽位）→ ~20s+；慢 URL 可队头阻塞所有 URL 的 fall-through。

**修复方向：** `acquire(timeout=REQUEST_TIMEOUT)` 超时后放弃直连（重查缓存，无则返回 None）；或按 URL 分组信号量。已申报副作用"极端情况额外 0.5s"不准确——实际最坏吃满整个 REQUEST_TIMEOUT 队列。

### P2-5 【P2-13 残留】stock_api.py:233-243: budget 在获得锁前计算，等待期消耗 deadline

**触发与后果：** 当 {多线程并发抢占同一 CDP page 锁（MAX_WORKERS=20 × 5 页）} 时，队尾线程用**陈旧 budget**（锁前计算）运行 `evaluate_fetch`，可能超过自身 `deadline` 并继续占用下一页锁，fallback 路径延迟被放大（已申报副作用，但未提预算陈旧导致的超 deadline 执行）。

**修复方向：** 获得锁后重算 `budget = min(deadline - time(), 2)`，若 ≤0 直接 break。

### P2-6 【P1-5 残留】stock_api.py:185: log.warning 无异常详情

`log.warning('[after] callback failed for %s', code)` 不含异常对象/回溯，无法定位失败根因。建议 `log.warning(..., exc_info=True)` 或附加 `e`。行为不变，仅可见性——申报的副作用描述准确。

### P2-7 【防御性说明】stock_api.py:129-133: 截断先于去重 + docstring 与实现顺序不符

截断发生在 `seen` 去重之前：理论上 60 个含 15 重复的入参会被截到 50 再去重成 35，上限内本可处理 45。当前实际不可达（server 先截、stream 传 set 无重复），但 docstring "Steps: dedupe -> validate" 与新顺序不符。修复 P1-1 时一并调整顺序（先去重再分片）并更新 docstring。
